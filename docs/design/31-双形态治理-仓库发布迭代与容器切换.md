# 31 - 双形态治理：仓库、开发、发布与容器切换

> 状态：**设计定稿（D1–D4 按建议暂定，如有异议随时改）**。本文回答：基座形态与 superagent 形态如何保持独立又共享迭代——git 仓库管理、开发与迭代流程、规范规则、容器内切换。
> 决策原文（2026-11-17）：保持两个版本独立，产品化时可选择轻量化基座形态；bug 修复与插件迭代两版都需要，后续开发流程要能及时更新两个版本。
> 关联：`24-主动工作体系融合设计`、`26-扩展模型`、`29-统一工具编排`、`32-最终态开发方法`（两题互锁）、`docs/eterna-web-profile.md`、`docker-compose.yml`、`docker/entrypoint.sh`、`market/`
> 日期：2026-11-17

---

## 0. 一句话结论

**"两个版本"不是两个代码库，是同一个 monorepo 的两个装配形态（form）**——独立性表达在挂载面、发布流、数据卷上，不在代码分叉。同仓方案下"及时更新两个版本"**结构性消失**：代码同步问题不存在，只剩发布时机问题。

---

## 1. 现有地基（三块事实，方案落在其上）

1. **形态本来就是模板驱动的**：`docker-compose.yml` 挂载 `docker/profile/cordis.patch.yml.template`（只读），entrypoint 按模板哈希门控渲染卷内 profile（模板未变保留用户文件与插件启停状态，变更才重渲染+移植；2026-11-18 起移植含工坊托管值——persona/section/maxBytes 6 条按基线快照判定后搬入新渲染，模板基线自身更新照常落地）——双模板只需复制此机制；
2. **装配产物先例**：market 已有 `glue-bundle` / `pack-bundle` 两种 bundle；
3. **双档先例**：`profiles/eterna-web` 与 `profiles/eterna-embed` 同仓共存，各自 boot 门禁（`verify-eterna-web.mjs` 模式可复制）。

---

## 2. 方案五件套

### 2.1 形态定义（配置即形态）

| 形态 | profile 模板 | bundle 产物 | 版本流 |
|---|---|---|---|
| **eterna-base**（基座版） | 现挂载清单不变（glue / llm-doctor / brand / panel / prompt-studio / llm-openai / access / usage-stats / compaction / attachments / memory） | `base-bundle` | 慢速、稳定 |
| **eterna-super**（superagent 形态） | base ⊕ tasks + channels 挂载 + interact 接线 + workbench + toolkit | `super-bundle` | 全速演进 |

### 2.2 插件分级（防基座腐化的关键）

- **Tier 1 基座共享**：现有 20 个 L1 包；
- **Tier 2 super 专属**：tasks、workbench（panel 扩展半边）等新增包。

**三条铁律**：

1. **依赖单向**：Tier2 → Tier1 允许，**Tier1 永不 import Tier2**；
2. **Tier1 为 super 演进的新能力默认关闭**（如 governance 规则版本化、interact Attention 台账——代码在，base 运行时不变）；
3. **双门禁**：动 Tier1 的 PR 必须同时过 `verify-eterna-base` 与 `verify-eterna-super` 两个 boot 门禁；动 Tier2 只过 super 门禁（monorepo 级 lint/typecheck 照跑）。

### 2.3 开发流程

单 main 干线 + 短命特性分支（沿用现有 AGENTS.md 规则：git push 单独确认）。**无长命版本分支**。

### 2.4 发布流

- 双 tag 独立节奏：`base-vX.Y.Z`（慢速）与 `super-vX.Y.Z`（全速），各自 CHANGELOG；
- 共享插件（Tier1）修复落 main → 两形态下次发布自动携带；
- 基座急需 hotfix：从 `base-vX` tag 拉 `release/base-vX` 维护分支 cherry-pick（super 挂载是严格超集，共享修复天然两版都有）；
- 同一 commit 可同时打两 tag（版本对齐发布）或分别择机。

### 2.5 容器切换（落在现有机制上）

| 项 | 方案 |
|---|---|
| 镜像 | **单镜像不变**（`eterna-agent:x.y.z`） |
| 模板 | 一分为二：`cordis.patch.yml.template`（base，现有）+ `cordis.super.patch.yml.template`（super） |
| 选择 | `ETERNA_FORM=base\|super` 环境变量 → entrypoint 选模板渲染（哈希门控机制原样复用） |
| compose | `docker-compose.yml` **保持基座**（现网 NAS 部署零改动）+ 新增 `docker-compose.super.yml`（super） |
| 端口 | base 3210（现有）/ super 3220 |
| 数据卷 | **分离且永不互通**：`eterna-home`（base，现有）/ `eterna-super-home`（super） |
| 切换语义 | **切换 = 并存**（两个 compose 项目同时跑），不是原地变形；Schema 前向守卫（新 schema 拒启，store 已有此纪律）保证 super 写过的卷不会被 base 误开 |

---

## 3. "轻量化"的重新定义

base 的轻，在于**挂载面 / 内存 / 攻击面 / 供应链**，不在于代码行数——Tier1 里为 super 演进的休眠代码（默认关闭）是可接受代价。想清这一点，"保持独立"与"共享迭代"不再冲突。

---

## 4. 规范规则汇总（CI 与评审清单）

1. `packctl form-check`（新增子命令）：Tier1 不得 import Tier2；两份挂载清单与两份模板一致；
2. 双 boot 门禁进 CI（复制 `verify-eterna-web.mjs` 模式出 `verify-eterna-super.mjs`；现名可改名 base）；
3. Tier1 新能力默认关闭（评审项：PR 必须说明默认状态与两形态影响）；
4. 双 tag 双 CHANGELOG；
5. 数据卷隔离 + schema 前向守卫；
6. 沿用：git push 单独确认、README 数字实测可追溯、UI 中文。
