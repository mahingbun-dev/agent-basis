# 46 · 角色模型选择策略(master / worker / 评估)

> 状态:**已落地(2026-11-19)**。触发:用户提问「superagent 模式下配置了这么多模型供应商,
> worker 和主 agent 应该如何选择模型进行请求?策略是什么?」本文件记:改前事实(§一)、
> 拍板策略(§二)、实现与配置路径(§三)、验收(§四)、边界与后续(§五)。
>
> 一句话:DSH 的会话模型只有一个来源(部署默认模型);46 号把它补成**按角色双槽位**——
> `eval.model` 管主会话、`executor.model` 管 worker,各自经 `agent.model.select` 在会话
> 建成/取回时播种;两者 null 即维持改前语义(随宿主默认,不覆写)。

## 二、拍板策略(2026-11-19)

| 角色 | 设置键 | 职责 | 建议档位口径(operator guidance,**非强制**) |
|---|---|---|---|
| orchestrator(主会话) | `eval.model` | 理解人的意图、评估候选卡、`orchestrator_route` 裁决、回执措辞 | **强推理档**:评估与裁决质量直接决定"是否出票/出什么票",且调用量小;可配 `reasoningEffort: high` |
| worker(工单执行) | `executor.model` | 长跑多步工具调用、写盘、交付物产出 | **执行型档**:快、便宜、tool-call 稳(coding 能力优先);成本大头在 worker,主会话档位尽量别下放到这里 |
| 两者均 null | — | 不覆写,随宿主默认(改前语义) | 单模型部署/试跑期保持缺省;super 生产形态建议显式配 worker 档(见 §三-4) |

规则:

1. **配置在场即覆写**:非 null 时该角色恒用此模型;`agent.model.select` 对同档是原子 no-op,
   异档落 `model/selection` 事件(宿主 pre-step 仅当会话用过别的路由才补一条 model changed
   提示语,新会话首轮无提示)。
2. **播种时点**:`Sessions.ensure` 解析/建成会话后、**任何投递之前**调 `select`——宿主在下
   一步的 pre-step 才捕获 `model.current()`,因此首轮第一步即用角色模型
   (`packages/access/src/thinking-auto.ts` 同款纪律:select 必须早于驱动唤醒)。
3. **新建与复用同播**:worker 每工单 `worker-<ticketId>` 新建走一次;重启 resume 的 master
   会话同样重播——配置恒为准,不因进程重启漂移。
4. **热改现读**:`roleModel` 是装配注入的 getter,每次 ensure 现读租户 settings;主会话工具
   或面板改设置后,**下一次建/取会话**即生效,不需要重启进程。
5. **fail-neutral**:Agent 无 `model` 结构面(假件/未来实现)或 `select` 抛错时,记一条
   warn 跳过播种——权限/标题半边照旧,角色模型是增强面,不能成为建会话的硬依赖。

## 三、实现与配置路径

| 面 | 落点 | 说明 |
|---|---|---|
| 播种 | `packages/tasks/src/session/sessions.ts:196-232` | `ensure()` 复解析后 `seedModel(agent, role)`;结构端口 `SessionsHost.roleModel?: (role) => RoleModel?`(sessions.ts:134),不 import 宿主类型 |
| 装配 | `packages/tasks/src/plugin.ts:609-616` | `sessionHost` 未显式带 roleModel 时注入 getter:`orchestrator → store.settings().eval.model`、`worker → executor.model`;显式注入恒优先 |
| 配置入口 | 主会话工具 `orchestrator_settings_save`(`packages/tasks/src/tools/orchestrator.ts:343`) | `block='eval'` / `block='executor'`,**value 必须是整块**(`mergeBlock` 按块 schema 解析,缺键取缺省),经人在场显式请求保存(工具纪律:不主动改配置) |
| 设置存储 | 租户 `tasks.sqlite3` 的 settings(版本史 `saveSettings`) | 面板/工具同源;部署级 YAML 不承载这两键 |

一次合法的 executor 块示例(值须取 `/api/session/modelCatalog` 中真实存在的 provider/model,
写错会在 worker 首轮请求报 llm 路由错误):

```jsonc
// orchestrator_settings_save { block: "executor", value: { ... }, revision: N }
{
  "model": { "provider": "llm-pi-ai", "model": "<执行型模型 id>", "reasoningEffort": "low" },
  "maxWorkers": 3, "directory": "", "prepare": "", "blockedCommands": []
}
```

配置语义补充:

- **worker 未配 `executor.model` 时仍随部署默认**——而部署默认会被 UI 换模型改写(§一-2)。
  这不是缺陷而是缺省语义;super 生产形态建议显式配 `executor.model`,把「主会话换模型」
  与「工单用什么模型」解耦。
- 模型 id 与 `reasoningEffort` 档名以该模型在 catalog 的 `reasoning.efforts` 为准;不支持的
  档名不会被播种侧吞掉,会在请求准备期报错(故障可见、不静默降级)。
- `eval.mode`(off/observe/auto)与 `eval.model` 正交:前者管是否受理,后者管主会话用哪个模型。
