# 54 - 会话历史首屏分页与「加载更早」

> 状态：已实现（2026-11-24）。起因：用户反馈「载入历史有点慢」，要求只加载最后 30 条、其余走「加载更多」每次 30 条。

## 0. 一句话结论

上游（DSH rc.5）把每次历史请求的消息预算写死在客户端 bundle 内：**500 条消息 / 至少 2 个 turn**。长会话首屏一次就取回近乎整份日志（生产实测最坏 **14.22 MB / 3,677 条事件**），前端因此长时间停在「载入历史…」，而产品自带的「加载更早」按钮**永不出现**。修法不是改上游，也不是自建页面：在 Host 侧守卫层把 `events`/`page`/`follow` 的入参预算收到 **30 条**，首屏降到 **0.48 MB**，其余由「加载更早」按同预算续取。

## 1. 改前事实（全部实测 2026-11-24）

### 1.1 慢的是首屏体积，不是 Host 算力

扫描生产会话树 `~/eterna-data/super/sessions`（218 份 `session.v4.jsonl.zstd`），用与上游 `paginate` 同构的算法复算首屏：

| 指标 | 值 |
| --- | --- |
| 最坏会话 | 3,677 条事件 / 14.22 MB JSON（首屏一次过线） |
| 该会话压缩体积 | 4.2 MB（zstd） |
| Host 侧解压 + JSON.parse 全量 | **139 ms** |
| 首屏 >2 MB 的日志 | 8 份 |
| 首屏 >5 MB 的日志 | 3 份 |
| 首屏体积中位 | ≈0（多数会话本就短） |

结论：Host 处理只要 139 ms，**瓶颈是 14 MB 走网络 + 浏览器解析/渲染**。首屏里 `assistant/message` 一项就占 9.1 MB。

### 1.2 首屏为什么这么大

上游客户端在 bundle 内写死：

```js
// dsh-api-session-controller lib/client.js（源码 session.ts:54）
HISTORY_PAGE_OPTIONS = { maxMessages: 500, turnWindow: { minMessages: 50, minTurns: 2 } }
```

`paginate`（`lib/history.ts:132`）以**消息条数**为预算，而单个 Turn 内的 `tool/result`、`job/*` 与长 assistant 正文**也各占一条记录**——会话越"干活型"，每条消息携带的字节越多。触发条件是「累计到 2 个 turn」或「500 条消息」，长会话在一次 Turn 内就能撞满。

### 1.3 上游 UI 本就有分页，只是从未被触发

`ChatView.tsx:239` 有「加载更早」按钮，`hasMore`/`loadingOlder` 状态齐备，`session.loadOlder()`（`session.ts:419`）走 `beforeSeq` 游标续页。**缺的只是首屏窗口过大导致 `hasMore=false`，按钮不出现。**

## 2. 修法

### 2.1 选型：Host 侧运行时包装，不动上游

| 方案 | 结论 |
| --- | --- |
| 改 node_modules / 打 patch | ✗ 镜像每次重建都冲掉；违反「deepseek-harness 只读」 |
| 自建会话面板页面 | ✗ 违反前端铁律 1（不自建独立页面入口） |
| 客户端改页大小 | ✗ 页大小写死在第三方 bundle，且客户端不可注入上游 Session 类 |
| **Host 侧包装三个入口的入参** | ✓ 沿 `login-gate.ts`/`mux.ts` 既有先例；`dispose` 可完整还原 |

### 2.2 实现（`packages/access/src/history-window.ts`）

- `clampHistoryWindow(request, pageMessages)`：把 `maxMessages` 收到 `min(请求值, 30)`——**只降不升**，未来客户端改小无需改本层。
- `turnWindow` 是「至少多少条/多少轮」的**下限**规则，与上限冲突会被上游 `validateHistoryWindow`（`lib/history.ts:33-48`）判 `gateway/bad-request`，故 `minMessages > maxMessages` 时整体丢弃，退化为纯消息数分页。
- `installHistoryWindowClamp(service)`：包装 `events`/`page`/`follow` 三个实例方法，保 `this`、`follow` 的 AsyncIterable 语义原样、返回幂等 `dispose`。入口缺席/属性不可写时**静默跳过**，不上抛。
- 装配点：`plugin.ts` 经 `ctx.inject(['sessionController'], …)`（服务可能晚挂载），失败只记审计事件 `access.history.window`。
- 预算可配：`ETERNA_HISTORY_PAGE_MESSAGES`（缺省 30，非法值回落缺省），已进两份 compose。

### 2.3 轮次跳转必须放行

上游 Turn 导航跳到未加载回合时，以 `turnWindow.minMessages = 200`（`JUMP_PAGE_MESSAGES`）循环回补。把这种页也压到 30 会让跨千条事件的一次跳转变成上百次串行 RPC，故识别 `beforeSeq 存在 && minMessages ≥ 200` 并**原样放行**。若上游日后改了该取值，识别失效只会退回「压到 30」——语义仍正确，仅跳转变慢。

## 3. 验收（实测可追溯）

### 3.1 真实会话端到端（最坏会话 3,677 条事件）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 首屏事件数 | 3,666 | 219 |
| 首屏体积 | **14.22 MB** | **0.48 MB** |
| 「加载更早」页数 | — | 15 页，可完整回补到 seq 0 |
| 续页单页最大 | — | 2.57 MB（中位 ≈0.8 MB） |

续页仍有 2 MB 级页属**上游既定语义、本层不动**：`paginate` 会把消息按 `sourceEventSeqs` 展开到整组起点（`lib/history.ts:154-160`），压缩检查点等复用事件的来源组可跨数百条记录；拆开会让一条消息失去来源上下文。续页由用户点「加载更早」按需触发，不阻塞首次进入。

### 3.2 机制验证

- 单元测试 23 项（`packages/access/tests/history-window.spec.ts`）全绿。
- 生产容器内以真实 `SessionController` 类验证：包装后 `events`/`follow` 收到 `{maxMessages:30}`、`follow` 仍是 AsyncIterable、`dispose` 还原为 500。
- 网关分发面确认：上游以 `ctx.extend({invocation}).get(service)` 取接收者后 `Reflect.get` 方法（`api/gateway/src/index.ts:858`），实例级覆盖**对该路径可见**（已在 cordis 4.1.0 实测）。

## 4. 风险与回滚

| 风险 | 处置 |
| --- | --- |
| 上游改 `JUMP_PAGE_MESSAGES` | 识别失效→跳转页被压到 30：语义正确、变慢；升级时复核该常量 |
| 上游改方法名/形态 | `installHistoryWindowClamp` 返回 undefined，审计记 `ok:false`，行为退回上游缺省 |
| 用户觉得每页太少 | `ETERNA_HISTORY_PAGE_MESSAGES` 调大即可，无需重建镜像 |
| 回滚 | 删装配块；或把 env 设为 500 即等价原状 |
