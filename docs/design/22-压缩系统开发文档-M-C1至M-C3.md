### C3 摘要结构校验

**新导出**（放 `summarizer.ts` 底部，供 evals 复用）：

```ts
/** 段落解析结果：标题 → 段正文（trim）。 */
export interface SummarySections { readonly titles: readonly string[]; readonly bodyOf: (title: string) => string }
export function parseSummarySections(summaryText: string): SummarySections
export const REQUIRED_SUMMARY_TITLES: readonly string[]   // 8 个 '## ' 标题，与模板逐字一致
export class InvalidSummaryError extends Error { constructor(readonly violations: string[]) }
/** 校验：标题齐备 + 关键两段非空非 '(none)'。违规聚合进一条 InvalidSummaryError。 */
export function validateSummaryStructure(summaryText: string): void
```

- 解析器：按行扫描 `^## ` 收集；`bodyOf` 取标题到下一标题之间的非空行 join。
- 关键段常量：`['Primary Request and Intent','Current Work']`；正文 trim 后为空或全为 `(none)` 即违规。
- **接入点**：`region.ts` summarizeCompaction 内、shrink 校验（:417）之前：对 `summaryToText(summaryResult.summary)`（text block 拼接，新增小 helper）调 validate；抛 `InvalidSummaryError` → 走既有 recover 循环（无监听者→重抛→compactPressure 重试）。校验失败最终也落一个带 error 的 `compaction/end`（region 既有失败路径）→ admin 侧可从 end.error 统计（C9）。
- 宽容边界：其余段允许 `(none)`；只拒"缺标题"与"双关键段空"。

**验收**：单测四型（正常/缺段/双关键空/其余段 none 合法）；golden 中含一个"摘要模型输出空壳"注入用例断言被拒并重试。

**facts.json schema**：

```jsonc
{
  "userVerbatim": ["把阈值调到 0.9", "..."],      // ≥5，须逐字出现在摘要
  "filePaths": ["packages/compaction/src/basic/config.ts", ...],  // ≥8
  "errorStrings": ["MODEL_SWITCH_COMPACTION_FAILED", ...],        // ≥3
  "commands": ["pnpm --filter @eterna/compaction run verify", ...], // ≥3
  "decisions": [{"claim":"thresholdRatio 保持 0.8","evidence":"…原文句子…"}], // ≥3
  "mustNotAppear": ["<原文没有的断言样例>"]        // 误报注入检测（可选）
}
```

**评分算法**（score.ts，纯函数，输入=摘要文本+facts，输出=逐项命中表+汇总）：
- 召回：userVerbatim/filePaths/errorStrings/commands 用 substring（大小写敏感，路径逐字）；decisions 用 evidence 句的关键 token 集合（≥80% 命中）；
- 误报：摘要每个 bullet 若不含任何 facts 证据 token 且非结构性陈述 → 标记 `unverified`（提示人工/judge 复核；首版不自动判死刑）；

### C6 陈旧工具结果清理层（stale-pruner 插件）

**新文件** `packages/compaction/src/stale/index.ts` + `stale/config.ts` + `stale/types.ts`：

```ts
export interface StalePruneConfig {
  keepGroups: number          // 默认 5：按 turn 分组保留最近 N 组
  minSavingsTokens: number    // 默认 4096：预计回收不足不动手（一次清够，防碎片化缓存失效）
  thresholdRatio: number      // 默认 0.7：会话压力达 effectiveWindow×0.7 即触发
}
export class StaleToolResultPruner extends Service {
  static inject = ['tokenMeter']
  static Config: z<StalePruneConfig>
  pruneStale(session: Session, contextWindow: number): StalePruneResult | null
}
declare module '@deepseek-ai/cordis' { interface Context { staleToolResultPruner?: StaleToolResultPruner } }
```

**算法**（`pruneStale`，确定性、无 LLM）：
1. `ctx.tokenMeter.measure(session)` → `totalTokens < floor(W×thresholdRatio)` → null；
2. 枚举 surface 节点读 `tool/result` 事件（读法循 S'-1 结论；按 `data.turn` 分组降序）；
3. 豁免：最近 `keepGroups` 组；`data.error` 非空的结果（失败证据保留）；非文本主导块（含 image 等富块）的结果；
4. 计算预计回收 = Σ(estimateMessage(原文) − 512 占位估价)；< minSavingsTokens → null；
5. 对每个目标：**照 pruner 协议逐节点**——append `compaction/prune`（shadowedTokenCount=原文价）→ append `tool/result` 同 data + 替换 content 为单文本块 `[... tool result cleared (stale): 原始记录保留在会话日志，可回放查看 ...]` + `surfaceOp replace` + `sourceEventSeqs:[seq]`；
6. 返回 `{pruned: [{seq,turn,shadowedTokenCount}], savedTokens}`。

**触发**：插件自身监听 `agent/pre-step`（在 compaction-basic 之前：patch.yml 行序排前 + basic 的 pre-step 处理时压力已降）——`pruneStale(agent.session, headerContextWindow)`；contextWindow 取 `ctx.llm.resolveModelInfo`（照 basic/index.ts:423 先例）或 requestHeader（取现成，避免异步——实现时择一并在注释说明）。**不动消息结构、无 compaction/start|end 锁**（单节点原子替换协议与 pruner 一致）；不处理并发压缩互斥（append 串行天然安全，若实测冲突退化为挂进 basic 的 compactPressure 头部调用——退路写注释）。

**挂载**：eterna-web 两 preset 的 compaction 组内加行 `- id: stale-tool-result-pruner, name: '@eterna/compaction/stale-plugin', config: {keepGroups:5,minSavingsTokens:4096,thresholdRatio:0.7}`；group isolate 增 `staleToolResultPruner: true`；package.json exports 增 `"./stale-plugin": "./src/stale/index.ts"`。**此项改 profiles/eterna-web/cordis.patch.yml → 过 gate（与 C8b 同批，见 §8）**。

## 8. workflow 编排规格（脚本蓝图）

**总原则**：与记忆系统 workflow（`dwfrun-2bede33c`，label 含"记忆系统"）在同一工作区并行；包级工作不等待，**冲突工作过 gate**。

**冲突 gate 定义**（gate 步骤 = 一个子 agent 执行）：
1. 调 `ListWorkflowRuns` 查 label 含"记忆系统"的 run：
   - 无 running → 通过（若最近 run 状态 errored/stopped → escalate 问用户是否继续）；
   - running → `sleep 300` 后重查，循环上限 24 次（2 小时）；超限 escalate 问用户"记忆 workflow 仍在运行（当前 phase X），是否继续等待/跳过冲突项继续无冲突项？"；
2. 通过后：`git status --short` 记录起点（记忆工作区改动属预期，不惊慌、不清理、不 add 它们的文件）；若记忆 workflow 已完成且做了 commit → `git log` 确认后正常开工；
