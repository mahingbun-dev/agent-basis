## 0. 摘要：四问一句话答案

| 问题 | 结论（证据见 §3-§4） |
|---|---|
| 何时压缩 | 预测性阈值 + 分层泄压 + 溢出兜底 + 熔断，四件套缺一不可。主流落点在有效窗口的 70%-95%，公式化"窗口 − 输出预留 − buffer"优于裸百分比；触发太晚受 context rot 损失，太早则白付压缩延迟（端到端 +20-80%，arXiv:2609.32961） |
| 压缩策略 | 分层递进：单条工具结果落地截断 → 陈旧工具结果批量清理（确定性、零模型成本）→ 全量结构化 N 段摘要（保留最近轮次原文、增量合并旧摘要、KV-cache 友好调用）→ reactive 兜底。摘要后现场重建（重读文件/重注入指令）是保真的最后一环 |
| 如何不丢 | 六层防丢：durable 原文副本 → 结构保留（尾段原文/tool 对/boundary 元数据/时间线声明）→ prompt 级防丢（用户消息与安全约束逐字、工件踪迹、错误修复）→ 重建层 → 跨 session 记忆分层 → 校验与评估回归。核心红线：**摘要永远不该是唯一副本** |
| 如何评估 | 四层：离线关键事实召回/证据保留率 → LLM-as-judge 六维 → 配对续跑成功率（Compact-Bench 式）→ 在线重取成本/缓存命中。红线：**压缩比不是质量指标**（Factory 36,611 条生产消息评估）；只看任务完成率会漏检成本转移（5x 压缩下检索调用 ×3，arXiv:2608.16370） |

本产品判断：**机制骨架已是业界主流形态**（8 段结构化摘要 + KV-cache 复用 + 尾段保留 + 增量合并 + durable log 全留 + 四触发路径 + 先剪后摘），领先多数开源 CLI 实现；短板集中在**保真校验、陈旧清理层、评估体系、压缩×记忆联动**四处。优化方案见 §6。

## 1. 本产品现状（全部实测可追溯）

### 1.1 组成（三层）

| 层 | 实现 | 位置 |
|---|---|---|

### 1.2 触发（四路径，`basic/index.ts`）

1. **步间压力自动**：`agent/pre-step`（`basic/index.ts:251`），阈值 `floor(min(W×0.8, W−maxTokens预留−65536))`（默认 `thresholdRatio=0.8`、`retainRatio=0.16`、`headroomTokens=65536`，`basic/config.ts:20-23,83`）；压力达标后**先 `pruneSession` 泄压、复测仍超才摘要**（`basic/index.ts:440-446`）——已是分层递进形态。
2. **溢出恢复**：`agent/request-error` + context-overflow 错误码（`basic/index.ts:309`），pruner → 强制压缩 → retry，`maxOverflowRetries=1`。
3. **模型切换**：`agent/request` 前按新模型窗口重计价（`basic/index.ts:278`）。
4. **手动 `/compact`**（`basic/index.ts:503`）。

配置热更新：`$DSH_HOME/.eterna/compaction.config.json`（mtime 热应用，`basic/index.ts:177`；可热改仅 `auto/thresholdRatio/retainRatio`）。

### 1.3 摘要算法

- **8 段结构化模板**（`summarizer.ts:32-67`）：Primary Request and Intent / Key Technical Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step / Critical Context；要求逐字保留路径/命令/错误串/数字/签名；**遇已有 `<compacted-summary>` 块时增量合并去旧而非照抄**（`summarizer.ts:66`）。
- **KV-cache 复用**：复用会话自身 system prompt + tools + 消息前缀，压缩指令作为最后一条 user 消息（`summarizer.ts:25-31`）。
- **摘要模型**：`summarizationProvider/Model` 未配置时用会话当前模型（`summarizer.ts:127-137`）；eterna-web profile 未配置该键（`profiles/eterna-web/cordis.patch.yml:208-225` engine 配置留空）。
- 落盘：`<compacted-summary>` + `CHECKPOINT_PREAMBLE`，以 `user/message` + `surfaceOp replace` 单次替换（`region.ts:506`）；`compaction/start|end` 事件对作锁。

### 1.4 保留 / 丢弃 / 校验

- 保留：尾段 `retainTokens = floor((W−O)×0.16)` 逐字；system 头节点不入压缩区（`region.ts:131`）；不拆未闭合 tool-call/result 对（`region.ts:143-149`）。
- 摘要输入 = system 头 + **遮蔽段**（不含保留尾段，`summarizer.ts:79-84` SummarizationInput 注释）。
- 丢弃：被遮蔽段对模型不可见，**durable log 全保留**（上游 README；`docs/design/04-DSH源码设计笔记.md:24`），回放可确定性重现。
- 校验：仅收敛校验——摘要 framed token 必须 < 遮蔽段路由计价（`region.ts:417-422`），失败重试 `compactionRetries=1` 次。
- pruner：超 8192 字符的工具结果保 head 4096 + tail 1024 + 标记（`pruner/config.ts:10-14`）。

### 1.5 挂载差异

- eterna-web：两 preset 均挂 `compaction-basic + command-compact + tool-result-pruner`（`profiles/eterna-web/cordis.patch.yml:208-225, 364-381`）。
- basis-minimal：上游原版三件套（`basis/basis-minimal/cordis.patch.yml:61-65`）。
- **eterna-embed：无任何压缩**，仅 `maxTokens: 8192`（`profiles/eterna-embed/cordis.patch.yml:79`）。

### 1.6 已确认的缺口

1. `packages/compaction` **零测试**（对比 memory 包 80 测试，见 17 号文档 §5.1）。
2. 无摘要质量校验（唯一校验是 shrink 比较）与任何评估。
3. 无按**陈旧度**清理旧工具结果的层（pruner 只按单条大小剪）。
4. checkpoint 无"保留尾段时间线声明"（摘要写作时未见过尾段，但 preamble 未告知模型这一点）。
5. 无摘要后现场重建（文件重读/指令重注入）。
6. 压缩 × 记忆联动未落地（17:78 增量公告、19:107 `source=compaction` 强制 pending 均为规划态；memory 包现无任何事件挂点）。
7. 无 rapid-refill 熔断（压缩后快速回满 → 现有逻辑会再次压缩，无死循环检测）。
8. 无成本/收益观测（admin 统计仅 summaryCount/pruneCount/shadowedTokenCount/lastCompactedAt）。

### 2.2 ZCode 参考实现（同基座可直接对标）

- **触发公式（绝对值）**：`autoThreshold = (W − min(maxOutput, 21K)) − 13K`，200K 窗口 → 166K、128K → 94K；已废弃 95% 百分比阈值。token 计数优先用 provider 真实 usage，本地估算仅兜底（chars÷3）。**熔断三件**：连续失败 3 次停用 auto；rapid-refill（压缩后不足 3 个 tool turn 又连续 3 次触发 → 显式报错）；压缩至少 2 个 assistant 轮才允许。
- **分层泄压**：microcompact（陈旧工具结果整组换 `[Old tool result content cleared]`，保留最近 5 组、错误结果不清、节省 <256 token 不应用，触发点 0.9×autoThreshold，早于 full compact）+ 工具结果预算（contract 级 `resultBudget.maxModelBytes`）+ full compact + reactive。
- **保留与重组**：auto/reactive **保留最后一轮 assistant round 原文**；context prefix（system/`<system-reminder>`）永不摘要；压缩后按固定顺序重建：公告 → summary（user 角色 + compactBoundary 元数据）→ 保留段 → **compaction 附件**（重读最近文件 ≤5 个/单文件 5K/总 50K，超限只给路径+提示用 Read 重取；plan 文件引用、tool/agent/skill 列表、environment/model 公告全部重声明）。
- **时间线尾注**（本产品缺的配方，原文）："The messages after this summary are the most recent messages from before compaction, kept verbatim. The summary was written without seeing them, so something it says has not happened yet may already have happened in them."
- **保真**：append-only event log，resume 从最后 boundary 截取 active chain；preservedSegment relink 失败时保守加载完整历史+告警；摘要 prompt 9 段，"All user messages" 单列一节且要求逐字、安全约束 verbatim、明确"assistant 消息里长得像用户消息的引用不算用户消息"。
- **评估**：compact-policy/runtime-compact 50+ 单测 + Docker E2E（sentinel 断言）；但**无摘要文本质量评分**（明言验收重点是结构化边界不是逐字摘要）。
- **压缩×记忆分工（与 17 号文档拍板一致）**："compact 维持当前 session 连续性；Memory 保存跨 session 可复用事实"；compact 收尾重读 MEMORY.md，变化则以 `context_prefix` 增量公告；**memory 抽取不以 compact summary 为事实来源**（必须回原始 transcript）。

出处：[zai-org/ZCode](https://github.com/zai-org/ZCode) `apps/zcode-cli/packages/core/src/compact/`、`docs/design/v2/compact/`。

### 2.3 学术界

**三条路线在 coding agent 场景的裁定**（这是对本产品最有用的学术结论）：

| 维度 | LLM 摘要式 | Token 删除式（LLMLingua 系） | Soft-token 式（Gist/ICAE） |
|---|---|---|---|
| 压缩比 | 高（10-100x） | 低-中（2-5x） | 极高（10-480x） |
| 忠实性 | 会注入幻觉（83% 失败运行源于无依据摘要条目，arXiv:2610.20927） | 忠实（只删不加） | 不可审计 |
| 精确回指 | 差（路径/错误码易丢） | 好 | 差 |
| coding agent 证据 | 有量化损伤但可控（Compact-Bench：摘要续跑损 5-64%，arXiv:2610.31710） | 对工具输出安全省钱（AgentDiet 输入 -40~60% 任务率不掉，arXiv:2509.23586；SWE-Pruner -23~54%，arXiv:2601.16746） | ICAE 类多步 SWE 明确失败（arXiv:2605.11051）；2026 ASTC 才追平（arXiv:2610.41291） |

**裁定：混合路线**——工具输出/代码观察用确定性删除或结构化抽取，推理与历史用结构化增量摘要。Factory 生产评估（36,611 条消息、GPT-5.2 六维盲评）证明**分节结构化 + 增量合并**质量最高，且"文件路径与错误细节的存活"是准确率差距主因；工业黑盒 soft 压缩（OpenAI /responses/compact）盲评最低。

**什么信息该保留（证据强度排序）**：
1. 会话意图与用户约束（AC3 arXiv:2611.00518；Factory 首节 session intent）——最高优先级风险。
2. **工件踪迹**（文件路径、改动清单、错误信息、行号）——coding agent 最关键也最易丢；Factory 盲评中所有方法的 artifact trail 都是最弱项（2.19-2.45/5）。普通摘要救不了，需要文件状态跟踪。
3. 决策与理由、下一步计划（Factory：decisions/next steps 分节显著提升连续性，增量合并优于整体重生成）。
4. 错误教训："教训要留、过程可丢"——当轮推理文本延迟删除 100% 不伤效果（arXiv:2610.35496），但失败轨迹教训值得抽象保留（Reflexion arXiv:2303.11366 一族）。
5. 位置规律：重要信息置顶/置尾（Lost in the Middle，arXiv:2307.03172）。

**评估方法与红线**：
- 证据保留率：KEEP-Bench（arXiv:2610.26827，最优开源模型仅 66.8% 全证据保留）。
- 配对续跑：Compact-Bench（arXiv:2610.31710）。
- **完成率不充分**：5x 压缩任务完成率不变但检索调用 21→63.9 次（arXiv:2608.16370）——必须加交互成本。
- **压缩有隐藏延迟成本**：省 1/3 token 可能 +20-80% 端到端延迟（arXiv:2609.32961）——反对过频压缩。
- 触发时机本身可学习：AutoCompact（arXiv:2610.02163，SWE-bench +9.2%）。

### 2.4 企业平台级共识与非共识

**共识（各家独立收敛）**：
1. 压缩是长程默认原语不是紧急兜底（OpenAI 官方口号 "default long-run primitive, not an emergency fallback"，[compaction guide](https://developers.openai.com/api/docs/guides/compaction)）。
2. 最便宜的第一刀是清陈旧 tool result（Anthropic `clear_tool_uses_20250919` [context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)；处理完的文件内容/搜索结果进占位符即可）。
3. 文件系统是正外部记忆，让压缩**可逆**：路径即引用、内容可重取（Manus "file system as the ultimate context"；Anthropic memory tool `/memories` 多 session 进度日志模式；OpenAI skills + artifacts 落盘）。
4. KV/prompt cache 命中率是生产第一指标，上下文 append-only（Manus："the single most important metric"；Anthropic 规定清除与缓存的交互 `clear_at_least`）。
5. token 越多检索越差是普适规律（Anthropic context rot；Google 官方文档也承认多 needle 退化并建议"不必要的 token 别传"）——**大窗口消灭不了压缩需求**。
6. 重要状态必须在摘要之外独立保全（Anthropic 清除前预警写 memory；Cognition 压缩保"关键细节、事件与决策"；Letta memory block 逐字保核心记忆）。

**非共识（真分歧）**：
- 单 agent 长上下文 vs sub-agent 隔离（Cognition [反对多 agent](https://cognition.com/blog/dont-build-multi-agents) vs Anthropic 力推 sub-agent 只回传蒸馏摘要）。
- 扩窗口直塞（Google "all relevant information upfront" + caching）vs 压缩/检索（Anthropic/OpenAI 阵营）。
- 失败轨迹去留：Manus "leave the wrong turns"（删失败=删证据）vs Anthropic 优先清旧 tool result——折中是**把教训写进 notes 再清原文**。

## 3. 四问结论（综合裁定）

### 3.1 什么时候应该压缩

四件套，缺一不可：

1. **预测性阈值**：`有效窗口 − 输出预留 − buffer` 的绝对值公式（ZCode 200K→166K；Codex ~90% 绝对值；Claude Code ~90-95% 可调低）。业界区间 70%（Gemini，激进）到 95%；**过早压缩有真实代价**（压缩调用延迟 +20-80%，Codex 40% 就压被大量吐槽），**过晚受 context rot**（Cursor 用户：远未到限质量已退化）。本产品 0.8 + 65536 headroom 落在主流区间。
2. **分层触发**：确定性清理层应在更低阈值就介入（ZCode microcompact 0.9×autoThreshold；Anthropic context editing 独立阈值）——零模型成本，早做不亏。
3. **溢出兜底（reactive）**：provider 真报错后的恢复链（本产品已有）。
4. **熔断**：rapid-refill 检测（压缩后 N 个 tool turn 内又触发 → 报错而非继续压）+ 连续失败停用。这是防"压缩-填满-压缩"死循环烧钱的唯一手段（ZCode 已验证参数 3/3）。

附加触发（按需）：任务边界触发（阶段完成时压缩质量最高、干扰最小）、模型切换（本产品已有，业界少见的正确处理）。

### 3.2 压缩策略

分层递进 + 五个要点：

1. **分层递进**（成本从零到高）：单条落地截断（pruner）→ 陈旧工具结果批量清理（确定性占位符替换）→ 全量结构化摘要 → reactive 兜底。能确定性解决的不调模型。
2. **结构化 N 段模板**：意图/概念/文件/错误/待办/当前/下一步/关键上下文（本产品 8 段与 Claude Code/ZCode 同构，已是最佳实践形态）。
3. **保留最近轮次原文**（ZCode 最后 1 轮 / Codex 用户消息 20K / OpenCode 15K / 本产品尾段 16% 按预算）——保证"正在做的事"零损失。
4. **增量合并而非重写**（Factory 证据：漂移最小；本产品 prompt 已有该指令，领先 Gemini CLI/OpenCode 的整体替换式）。
5. **KV-cache 友好**：摘要调用复用会话前缀与 tools（本产品已有）；压缩后重建的消息顺序要稳定，避免无谓前缀失效（本产品 replace 单次落盘符合 append-only 精神，durable log 不改写）。

### 3.3 如何保证不丢重要信息

六层防线（本产品现状标注）：

| 层 | 手段 | 现状 |
|---|---|---|
| 副本 | durable log 永不删、可回放；摘要不是唯一副本 | ✅ 已有 |
| 结构 | 尾段原文保留、不拆 tool 对、boundary 元数据、**保留段时间线声明** | ⚠️ 前三有，时间线声明缺 |
| prompt | 用户消息逐字、安全约束逐字、工件踪迹（路径/错误串/签名）、错误与修复、防冒充用户消息 | ✅ 大部分有（8 段模板），"防 assistant 引用冒充用户消息"未显式写 |
| 重建 | 压缩后重读最近文件（≤5/单 5K/总 50K，超限给路径）、重注入 todo/plan/指令/记忆索引 | ❌ 缺 |
| 记忆 | compact 管 session 内，memory 管跨 session；抽取不以摘要为事实源 | 📐 17/18/19 已拍板未落地 |
| 校验 | 结构完整校验（8 段齐、关键字段非空）、shrink 校验、评估回归 | ⚠️ 仅 shrink |

### 3.4 如何评估压缩质量

四层，从离线到在线：

1. **离线 golden 回放**：构造带"关键事实清单"（用户指令逐字、文件路径、错误串、决策）的长会话 → 压缩 → 测清单召回率 + 误报率（摘要中出现原文没有的断言）。对标 KEEP-Bench 的证据保留率思路。
2. **LLM-as-judge 六维**（Factory 维度本地化）：准确 / 上下文感知 / 工件踪迹 / 完整 / 连续 / 指令遵循。
3. **配对续跑**（Compact-Bench 式）：同一长任务"压缩续跑 vs 全历史"完成率差；同口径跑"压缩后 N turn 内重取调用次数"（Read/grep 增量）——防成本转移漏检。
4. **在线运行时指标**：触发次数/rapid-refill 次数、压缩延迟、缓存命中率变化（cache-guard 数据源）、重取成本。

红线：压缩比不是质量指标（Factory）；"摘要更小"只是必要条件。

## 5. 不改的部分（明确保留）

- 阈值体系（0.8 / 65536 headroom / 16% retain）：落主流区间，无数据不动。
- 8 段模板 + 增量合并指令 + KV-cache 复用调用形态：业界最佳实践同构，19a 已立为先例。
- durable log 全保留 + replace 表面变更 + 事件锁：本产品相对 Gemini CLI 整体替换式的显著优势。
- "先 pruner 泄压再摘要"的既有分层（`basic/index.ts:440-446`）。
- 遵守上游约束（dsh-compaction README "已知限制"）：不注册面向模型的压缩工具（除非上游开放 seam）、不压 envelope、不可拆大单元交给 spill/image-offload。

## 7. 评估方案设计（P1-5 展开）

**资产**：golden 长会话集（≥10 条），每条附"关键事实清单"：
- 用户指令逐字（≥5 条，含至少 1 条纠正性反馈、1 条安全约束）
- 工件踪迹：文件路径（≥8）、错误串（≥3）、命令（≥3）、数字/签名（≥3）
- 决策与理由（≥3）、待办（≥2）

**流程**：回放会话 → 在指定点触发压缩 → 对摘要跑三类断言：

1. 客观指标（脚本）：清单召回率（逐项 substring/等价匹配）、误报率（摘要断言在原文无依据）、结构完整（8 段齐）、压缩比（仅记录不设目标）。
2. LLM-as-judge（六维，1-5 分）：准确/上下文感知/工件踪迹/完整/连续/指令遵循；judge prompt 与评分细则入库。
3. 续跑配对：压缩点后接标准任务集，对比"压缩续跑 vs 全历史"完成率 + 重取调用次数。

**门槛（首版基线，评估后修订）**：关键事实召回 ≥90%、用户指令逐字召回 100%、误报 = 0 硬红线、续跑完成率差 ≤10%。
**回归纪律**：任何 prompt/阈值/校验改动必须跑全量 golden 集，分数入库留档（对齐 AGENTS.md "数字实测可追溯"）。

## 8. 风险与边界

- **上游约束不可越**：envelope（system/tools）不压、不可拆大单元压不动（靠 spill/image-offload 配置规避）、压缩不注册模型工具——违反即破坏 dsh seam 契约与多租户铁律。
- **记忆投毒 C3 通道**：compaction 摘要固化污染内容（17 号文档已识别）——P1-4 的强制 pending 审批是闸门，评估 harness 中加投毒样例。
- **缓存交互**：新增清理层/重建附件都会改变消息序列，需过 cache-guard 的前缀稳定性检查（`packages/cache-guard`）；P1-1 的占位符替换要一次性替换到位（对齐 Anthropic `clear_at_least` 思想：一次失效，值得）。
- **不做**：token 删除式/soft 压缩路线（学界裁定对结构化工件场景不适用或不可审计）、百分比阈值下调至 0.7 以下（无数据支撑）、绕过上游自研 agent 循环内压缩。
