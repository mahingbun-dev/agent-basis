# 12 - 功能点总清单与承载方式决策(逐项确认表)

> 状态:**待逐项确认**。目的:实现前把全部功能点收拢,逐项标注承载方式;每个功能点必须在"改 DSH 内核 vs 插件"上获得确认。
> 承载方式图例:**A** = DSH 原生,配置/挂载即用(零自研代码) · **B** = L1 插件(bundle,走 ctx.* seam,不改内核) · **B'** = 外部工具/CLI(不进 agent 进程) · **S** = 规范/文件约定(纯约定) · **L2** = 领域包声明 · **D?** = 改内核候选(需单独拍板)

## 0. 承载方式判断准则(五条,全表适用)

1. **有 seam 吗?** DSH 开放了 ctx.tools / approval waterfall / turn-stopping / systemPrompt sections / 事件流 / storage / preset / config schema / UI renderer——有现成 seam 一律插件,不碰内核。
2. **插件能"强制"还是只能"引导"?** 安全类功能(出口管控、权限)必须强制;若插件只能在 pre-execute"引导"(如改写参数注入 proxy)而拦不住底层行为,才考虑动沙箱/内核。
3. **平台级还是行业级?** 行业差异永远进 L2 领域包;能进内核的只能是"所有行业都需要且 seam 表达不了"的东西。
4. **改内核的代价**:DSH 处于 pre-stable、有破坏性变更史(rc.3 全仓改名不留兼容)——私有内核 patch = 每次升级的合并税。**优先级:插件 > 上游 PR(MIT,可贡献回官方)> 私有 fork patch(最后手段)**。
5. **数据面 vs 控制面**:数据面(事件流、存储)DSH 已全开放;控制面(审批、规则)插件可挂 waterfall——两层都够用,无需改内核。

**总览统计**(**61** 个功能点):A 原生 ×16 · B 插件 ×35 · B' 外部工具 ×4 · S 规范 ×5 · L2 ×1 · **改内核候选 ×0(已清零:D-A/D-B 均拍板仅插件)——100% 零内核改动**。(2026-11-03 增补:通道加企微/邮箱双向 +7.6/7.7/7.8,领域包加工作台/对话式添加 +10.5/10.6)
