# 29 - 统一工具编排与工具路由（模型定制工具包）

> 状态：**设计定稿（§7 五问已于 2026-11-17 第二轮全部拍板）**。本文落实 2026-11-17 拍板的 B4 新方向：统一工具编排 + 工具路由，实现"任意模型表现与体感一致"。

## 0. 一句话结论

在应用层（聊天会话 / 任务 worker）与模型适配层之间插入一个**能力契约 + 工具路由**层：应用只声明"本轮要哪些能力"，路由器按「能力 × 本部署已配置的供应商集」选择实现（对话模型原生 → 跨供应商借用 → 通用兜底），所有路径产出**同一种规范化块格式**——体感一致靠协议收口，不靠逐模型对测试。

---

## 1. 五层架构

```
应用层（聊天会话 / 任务 worker）——只声明意图，模型无关
  「本轮要：web_search + read_url，不要语音」
        ↓
① 能力契约层     五个能力：web_search / read_url / files / tts / asr（版本化，全仓唯一定义）
        ↓
② 工具路由器     按「能力 × 已配置供应商集」查能力矩阵：对话模型原生 → 跨供应商借用 → 通用兜底
        ↓
③ 提供方适配器   deepseek（原生，chat-demo 即参考实现）
                glm（原生，字段级结论见 29a）
                mimo（原生，字段级结论见 29a）
                generic（通用兜底，客户端执行）
        ↓
④ 规范化块协议   所有路径产出同一种块结构（搜索步骤时间线 / 引用角标 / 来源卡 / 附件引用）
        ↓
⑤ 降级语义       矩阵中没有的能力 = 显式禁用态 UI，不是静默消失
```

各层职责边界：

| 层 | 职责 | 不负责 |
|---|---|---|
| ① 契约 | 定义能力枚举、声明参数、版本号 | 任何提供方细节 |
| ② 路由 | 矩阵查询、参数翻译（声明 → 提供方 API 形态） | 执行 |
| ③ 适配器 | 请求组装、流解析、结果翻译成 ④ | 会话状态 |
| ④ 块协议 | 规范化块类型（渲染与 prompt 的唯一消费物） | 提供方字段透传 |
| ⑤ 降级 | 能力缺失的显式表达（UI 禁用态 + 接口 unavailable） | 假装可用 |

## 2. 三个关键设计判断

### 2.1 体感一致 = 规范化块协议（枢纽）

不管底层是 DeepSeek 服务端工具、GLM 原生工具、还是客户端执行的搜索，最后都翻译成**同一种块结构**进会话。渲染层（`view.ts` 式投影）、prompt 组装、金集测试全部不用按提供方分支。**契约里禁止出现提供方特有字段**（如 DeepSeek 的 `encrypted_content` 只存在于 deepseek 适配器内部，翻译后丢弃或另存）。

### 2.2 chat-demo 是路由器 deepseek 分支的参考实现

- **参数控制调用与组合**：chat-demo 的 `serverTools(search)` 函数——按开关组装 `deepseek_web_search` / `deepseek_read_url` 声明进请求 `tools` 参数，正是 B4 决策说的"通过 API 参数控制工具包的调用和组合"；
- **流侧解析**：`server_tool_use` / `web_search_tool_result` / `web_fetch_tool_result` 块的类型与归并逻辑（`reply.ts` 的 `applyEvent`）现成；
- **附件与语音**：Files API（`anthropic-beta` 头 + `purpose` 二分）与 `/v1/tools/asr|tts`（PCM 24kHz）的接入代码可翻译复用；
- **结论：deepseek 分支基本零研究成本，是契约的第一个消费者与回归基准。**

### 2.3 通用兜底 = chat-demo 故意不做的那半边

chat-demo 无后端，遇客户端 `tool_use` 直接 `prefix: false`（`reply.ts:88`）。通用工具包补上这半边：模型发出工具调用 → 客户端执行（调搜索后端 / 读网页）→ 结果以 `tool_result` 回灌 → 以**相同的规范化块格式**产出。

**实施纪律**：generic 与 deepseek **并行开发**——generic 是能力契约的试金石；若契约只有 DeepSeek 形状，GLM/MiMo 接入时必然返工。两者的公共测试（同一组能力声明 → 同一组规范化块断言）进包级 vitest。

### 2.4 能力借用：路由键是「已配置供应商集」，不是「对话提供方」（2026-11-17 第二轮拍板）

体感一致的更进一步：**能力可以跨供应商借用**。主模型没有某能力时，只要部署里配置了有该能力的供应商，路由器就向出借方发起一次**能力侧调用**（如带 `deepseek_web_search` 声明的最小 chat 请求），解析其结果块并规范化回灌主会话——用户在 GLM 上对话，搜索仍可由 deepseek 原生执行。

供给链三段式：**对话模型原生 → 已配置供应商原生（借用）→ 通用兜底**（web 兜底 Tavily；语音兜底自托管栈，见 §7）。

代价与诚实：
- 借用消耗出借方一次**能力侧调用**——独立端点直调（GLM/DeepSeek，按次计费）或最小 chat 请求（MiMo，计 token）；
  - 29a 附-A 合并修正（2026-11-18 回填）：原拍板句「借用消耗出借方一次小额模型调用（其 API 计费）」对 GLM/DeepSeek 出借方不成立——GLM 与 DeepSeek 出借能力可直调独立端点、按次计费、无 token 成本，MiMo 是唯一需构造 chat 形态请求的出借方；各供应商计费明细见 36 号 §2.4「成本计费口径表」。
- 矩阵因此是**部署级**的（随配置集变化），doctor 探活须覆盖整条借用链。

## 6. 与既有系统的关系

| 系统 | 关系 |
|---|---|
| `packages/llm-openai` | **分层不同**：llm-openai 是传输适配（协议兼容层），toolkit 是能力层（语义）。见 §7-5 |

## 7. 拍板记录（2026-11-17 第二轮，五问全部落定）

### Q1 通用搜索后端 = 知识库优先 + 按配置启用 Web 源（含借用）+ Tavily 兜底

搜索供给链（拍板原文）：

```
① 内部知识库优先（FTS5 / WeKnora，产品已有）
② Web 层按「已配置供应商集」启用：
   对话模型自带原生 → 其他已配置供应商的原生（借用）
   例：主模型为 GLM 但配置了 deepseek → 直接调 deepseek 的 web search；
      配置了 glm / mimo → 优先各自原生的 web 源
③ 最终兜底：Tavily（商业 API，按部署配置）
```

要点：
- **路由键升级**（见 §2.4）：矩阵是**部署级**的，随配置集变化；
- **借用的实现形态**：向出借方发起一次独立的能力侧调用，解析其结果块并规范化回灌；借用消耗出借方一次小额模型调用（29a 附-A 修正注记，2026-11-18 回填：计费形态已细分为两档——独立端点直调按次计费或最小 chat 请求计 token，见 §2.4；本行拍板原文保留不改）；
- **SearXNG 方案弃用**。内网纪律：任何 Web 源（供应商原生搜索、Tavily）都意味着查询出网——矩阵如实展示该部署的搜索档位（仅内部 / 内部+原生 / 内部+原生+Tavily）；**未配置 Tavily 且无原生可用时 = 显式降级，绝不静默外发**。

### Q2 语音 = 完整开发（不分版本），策略与搜索同构

```
① 对话模型供应商自带的 ASR / TTS 优先（deepseek /v1/tools/asr|tts；mimo 待 R2/R5 核实）
② 其他已配置供应商的原生语音（借用）
③ 最终兜底：自托管开源栈（当前选型 FunASR + CosyVoice，经可插拔语音供给接口，可换）
```

- **Web Speech API 弃用**（Chrome 走 Google 服务 = 数据出内网 + 各浏览器质量不齐，违背体感一致）；
- 自托管语音作为 docker compose 内的一个服务交付（R7 研读部署面与基线）；
- ⚠️ 诠释确认项：拍板原话"跟 web search 的策略一样"，但 Tavily 无语音对等物，故兜底取自托管栈——如另有设想请指正。

### Q3–Q5 按建议确认

- **Q3 files 兜底 = 按类型混合**：图片对视觉模型 base64 内联；文档服务端文本抽取 + 体积上限；不可解析显式降级；矩阵如实标注 generic 为"文本级"、原生为"版面感知"；
- **Q4 矩阵配置面 = 模型设置页 UI 为主**（doctor 逐能力探活建议，覆盖借用链），静态配置作导入种子；
- **Q5 包边界 = 新建 `packages/toolkit`**，`llm-openai` 保持薄传输层。
