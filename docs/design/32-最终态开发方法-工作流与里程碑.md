> 状态：**设计定稿（取代 24 §6 的 P0–P3 分阶段路线）**。本文回答：superagent 形态如何"一步到位"——不分 Vn 阶段，把方案往最终态探索、调研、设计和开发。

---

## 0. 一句话结论

反对的不是"顺序"，是**中间态架构**——P0 造临时 Attention、P1 推倒重来的那种返工。解法：**按最终态设计、按技术依赖施工、单干线持续集成，不设计任何"过渡期产品形态"**——顺序由依赖决定，不由版本阶段决定。

---

## 1. 五条原则

1. **设计一次到位**：架构决策已在 24–30 号 + 三轮拍板闭环；剩余设计缺口只有三处且立即并行启动——tasks 包详设、toolkit 适配器详设（待 29 号 R1–R7）、工作台（待原型，30 号 §5 首批四件）。**不存在"先出简版设计"**。
2. **阶段 → 工作流**：五条并行工作流（§2）替代 Vn 阶段；顺序由技术依赖决定（契约→适配器；Engine 事件→工作台实接），不由产品阶段决定。
3. **P0 溶解**（§3）：原"还债"项全部成为最终态设计的组成部分，**不建任何临时物，就没有返工**。
4. **单干线 + 暗生长**：一切落 main，靠 31 号 Tier 规则 + 双门禁保证 base 形态不受扰动；super 形态的 main 就是最终态的连续生长，无长命分支。
5. **里程碑替代版本号**（§4）：M1–M5 都是**最终架构的纵切演示**（不改架构、只标记可演示点），不是产品版本。

| # | 工作流 | 内容 | 依赖 | 备注 |

```
关键路径:  WS-A tasks 内核 ──→ WS-E channels/interact 接线 ──→ M4 端到端 ──→ M5 试点
并行线:    WS-B toolkit（独立交付，聊天即受益）

           WS-D 工作台: 原型 + mock 先行 ──(实接)──→ WS-A 的 DomainEvents
```

## 5. 上线策略与开发策略分离（重要澄清）

**开发一步到位 ≠ 上线莽撞**。explicit-only 起步、`inferred` 观察模式、误报率 <10% 才放量——全部保留，但它们是**运行时 policy 开关**（superagent 的 accept mode 即此设计），不是代码阶段。发布时功能全部就绪，放开节奏由策略控制。两头都占：开发无拉扯，上线有缰绳。

---

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 长期无用户可见产出（士气 / 验证空窗） | ① **base 形态继续正常发版**（用户价值不断供，31 号双形态的红利）；② super 团队**每周 dogfood main**——自己先用起来 |
| 集成雪崩（工作流合拢时爆炸） | ① 每日双形态 boot 门禁；② 里程碑强制端到端纵切演示，**任何工作流不得"憋大招"超过一个里程碑** |
| 关键路径（WS-A）延误拖垮全局 | WS-B/C/D/F 均与其并行无阻塞；M1–M3 不依赖合拢，可独立演示维持动量 |
