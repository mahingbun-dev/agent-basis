# 48 · 容器数据持久化目录改造方案（宿主机专用数据区 + 子目录挂载）

> 状态：**讨论稿 v2（2026-11-19），未实施**。本文只做方案设计与施工计划，不改代码、不动现网。
> 目标：把 `docker-compose` 的 named volume（`agent-basis_eterna-home`）改为宿主机上一个专用文件夹区域，
> 按数据类别建立子目录并 bind mount 进容器；**容器内路径 `/data` 保持不变**。
>
> **v2 拍板（2026-11-19，P0-3）**：宿主根目录固定为 **`$HOME/eterna-data`**（家目录下
> 为本产品新建的专用文件夹；本机即 `/Users/sunny/eterna-data`），每个实例一个子目录
> （`super/`、`base/`、测试用 `test-<date>/`），整树单挂载到 `/data`。
>
> 关联：`docker-compose.yml`、`docker-compose.super.yml`、`Dockerfile`、`docker/entrypoint.sh`、
> `deploy/README.md`、`docs/docker-deploy.md`、`docs/design/31-双形态治理…`、`docs/design/47-上游DSH合并…`。

---

## 0. 一句话结论

**推荐方案 A：一个部署实例一个宿主根目录，整树单挂载到 `/data`**
（例：`${ETERNA_DATA_ROOT}/super:/data`），宿主根目录内按数据类别建子目录；
entrypoint 增加「`/data` 必须是 mountpoint」的持久化预检。

如果产品上必须做到「compose 里一条条列出子目录挂载」（方案 B），本文也给出完整清单与代价：
16 个目录 + 3 个根级文件，文件类 bind mount 需要额外处理，且未来上游新增路径会静默漏挂。
**建议 A 为默认，B 作为可选分盘模式。**

### 1.3 现网 profile 里已经有「用户态」

`profiles/eterna-super/package.json` 的 `dsh.profile.bundles` 已包含
`@eterna/hello-market`、`@eterna/knowledge-admin` 与 10 个 `@deepseek-ai/dsh-experimental-*` bundle。
这些是用户通过插件页/市场安装产生的事实状态，**不在仓库模板里**；迁移必须整树保留，
不能按仓库模板重建（否则插件丢失）。

### 1.4 硬链接与文件系统约束（方案分盘的硬阻断）

实测卷内 **7362 个多链接文件**：`profiles/` 3801、`.pnpm-store/` 3190、`market/` 371。
三者的依赖布局互相引用（`.pnpm-store/v11/projects/*` 是指向 `../../../profiles/...`、
`../../../market/...` 的相对软链）。若把它们拆到不同宿主文件系统（不同 btrfs 子卷、
NFS/SMB、不同磁盘），硬链接会退化为复制或直接失败，备份/恢复体积会静默膨胀。

**结论：`profiles` + `.pnpm-store` + `market` 必须在同一个文件系统内。**
这条约束本身就否定了「按子目录拆到不同磁盘」的默认用法；方案 B 只能用于同盘分目录。

### 1.5 懒创建路径（升级到 rc.5 后会出现）

现网尚不存在、但首次使用即落 `/data` 的路径（上游 `dsh-home-paths` / bundle 默认）：

| 路径 | 来源 | 处置 |
|---|---|---|
| `cache/attachments` | `dshCachePath('attachments')` | 纳入持久化 |
| `office-kit/outputs` | rc.5 `office-kit` 行 `dshHomePath('office-kit','outputs')` | **已拍板启用（47 B15）**；纳入持久化，保留 24h / 上限 512MB，自清理 |
| `dsh-runtimes/dsh-primary-runtime` | rc.5 `workspace-dependencies` 行（Desktop 专属） | 非 Desktop 形态不出现（web 显式禁用） |
| `children/` | subagent 子会话数据 | 纳入持久化 |
| `.env` | 某些包的 fallback | 不应出现；出现即安全审查 |

方案 A 单根挂载天然覆盖这些未来路径；方案 B 需要每加一条上游路径就改一次 compose。

### 1.6 其它实况

- 运行时写面：卷内 + `/tmp`（`dsh-spill`、`mcp-server.log`、编译缓存）+ `/root/.npm/_logs`；
  `/repo` 只读（镜像层），无运行时写入。
- `/data/.eterna/` 还包含 `memory-audit.jsonl`、`memory.config.json`、`portrait.md`、

- 工作区内每个租户有自己的 SQLite：`workspaces/<账号>/.eterna/{memory,knowledge}.sqlite3`、

- 现存最大 WAL：`workspaces/cherry` 642KB；全局 `.eterna` 280KB。热拷贝必然不一致。
- `/data/users/` 为空、`demo/` 与 `.eterna/routing-diagnose.json` 是测试残留，可清理。

## 2. 目标与非目标

### 2.1 目标

1. 数据落在宿主机可见的专用目录，可 `ls`、可 `rsync`、可整树打包；
2. 按数据类别有清晰子目录（profiles / sessions / storages / access / workspaces / market / …）；
3. 容器内路径不变（仍 `/data`、`DSH_HOME=/data`、`working_dir=/data`），**避免任何绝对路径失效**；
4. 单容器冷迁移可回滚；旧 named volume 保留为回滚点；
5. base/super 两形态各自独立目录，永不互通（沿 31 号 G4-7）；
6. 迁移后现有用户、会话、审计、插件、模型设置、令牌全部可用。

### 2.2 非目标（本期不做）

- 不做容器 root 用户/UID 重映射（保持 root 运行）；
- 不支持把数据根放在 NFS/SMB 等网络文件系统（SQLite WAL 不安全）；
- 不做热迁移/在线双写；
- 不做数据加密（宿主磁盘加密由宿主负责）；
- 不改变 DSH 内部目录名或 schema。

## 3. 宿主目录布局

### 3.1 推荐布局（方案 A：整树单挂载）

```text
$HOME/eterna-data/                        # 专用数据区（P0-3 拍板；本机 /Users/sunny/eterna-data）
├── super/                                # 当前生产形态（一个实例一个根）
│   ├── .anonymous-user-id
│   ├── .credentials.yaml
│   ├── .eterna/
│   ├── .pnpm-store/                      # 可重建，备份可排除
│   ├── access/
│   ├── agents/                           # 新增：DSH_AGENTS_HOME（见 §6）
│   ├── attachments/
│   ├── cache/                            # 新增：DSH cache（上游 rc.5 路径）
│   ├── demo/
│   ├── eterna-prompt-studio/
│   ├── knowledge-admin/
│   ├── knowledge.wiki/
│   ├── logs/
│   ├── market/
│   ├── memory-distill/
│   ├── office-kit/                       # 启用 office 后出现；outputs 24h/512MB 自清理
│   ├── profiles/
│   ├── relay-token
│   ├── sessions/
│   ├── storages/
│   ├── users/
│   └── workspaces/
├── base/                                 # 仅在并行跑 base 形态时需要
│   └── …同构
├── backups/                              # 冷备 tar/rsync，不挂进容器
└── exports/                              # 人工导出/迁移中转
```

规则：

- **一个运行中的实例一个根**（`super/` 或 `base/`）。两个容器同时跑时绝不共享同一个根；
- 宿主根由部署脚本 `install -d -m 0700 "$HOME/eterna-data"` 创建，**不纳入 git**；
  compose 只引用 `ETERNA_DATA_ROOT`，不引用相对路径；
- 根目录权限 `0700`；敏感文件保持容器内 `0600`；
- `backups/` 与 `exports/` 在数据根下、但**不挂进容器**，避免容器内进程可读备份。

### 3.2 与「一个实例一个根」的对应

| compose | 建议根 |
|---|---|
| `docker-compose.yml`（base，3210） | `${ETERNA_DATA_ROOT}/base` |
| `docker-compose.super.yml`（super，3220） | `${ETERNA_DATA_ROOT}/super` |
| 生产 `eterna-deploy/docker-compose.yml`（当前 `ETERNA_FORM=super`） | `${ETERNA_DATA_ROOT}/prod-super` 或 `super`（二选一，本文示例用 `super`） |

生产目前把 super 形态跑在 base compose 上（`ETERNA_FORM=super` + `external` 卷钉名）。
改造后不再需要 `external: true`，但要**保留 compose 项目名 `agent-basis`** 与容器名，
避免 `eterna-deploy` 目录名导致新项目/新容器。

测试实例不复制 compose：把 `container_name`/端口/实例子目录参数化为
`${ETERNA_CONTAINER_NAME:-eterna-agent}`、`${ETERNA_PORT:-3210}`、
`${ETERNA_INSTANCE:-super}`，默认值与生产现状一致；测试时用 env 覆写为
`eterna-agent-test`/`3108`/`test-<date>`，避免固定容器名撞生产（50 号 WP6-2）。

## 4. 挂载方案对比

### 4.1 方案 A（推荐）：整树单挂载

```yaml
services:
  eterna-agent:
    working_dir: /data
    environment:
      DSH_HOME: /data
      DSH_AGENTS_HOME: /data/agents
    volumes:
      - ${ETERNA_DATA_ROOT:?set ETERNA_DATA_ROOT in .env}/super:/data
```

- ✅ 16 目录 + 3 根文件 + 未来上游新增路径全部天然持久化；
- ✅ 迁移/备份/扩容只对一个树；
- ✅ 不会因为漏挂某个子目录而静默丢数据；
- ❌ compose 里只有一行，看不到「逐项」；子目录由初始化脚本/entrypoint 建。
- 适合：单盘、要求稳、后续会跟上游升级（新增路径不可避免）。

### 4.2 方案 B（字面逐项）：每个数据类一行挂载

```yaml
volumes:
  - ${ETERNA_DATA_ROOT}/super/.eterna:/data/.eterna
  - ${ETERNA_DATA_ROOT}/super/access:/data/access
  - ${ETERNA_DATA_ROOT}/super/attachments:/data/attachments
  - ${ETERNA_DATA_ROOT}/super/demo:/data/demo
  - ${ETERNA_DATA_ROOT}/super/eterna-prompt-studio:/data/eterna-prompt-studio
  - ${ETERNA_DATA_ROOT}/super/knowledge-admin:/data/knowledge-admin
  - ${ETERNA_DATA_ROOT}/super/knowledge.wiki:/data/knowledge.wiki
  - ${ETERNA_DATA_ROOT}/super/logs:/data/logs
  - ${ETERNA_DATA_ROOT}/super/market:/data/market
  - ${ETERNA_DATA_ROOT}/super/memory-distill:/data/memory-distill
  - ${ETERNA_DATA_ROOT}/super/profiles:/data/profiles
  - ${ETERNA_DATA_ROOT}/super/sessions:/data/sessions
  - ${ETERNA_DATA_ROOT}/super/storages:/data/storages
  - ${ETERNA_DATA_ROOT}/super/users:/data/users
  - ${ETERNA_DATA_ROOT}/super/workspaces:/data/workspaces
  - ${ETERNA_DATA_ROOT}/super/agents:/data/agents
  - ${ETERNA_DATA_ROOT}/super/cache:/data/cache
```

三个根级文件怎么办：

| 文件 | 处理 |
|---|---|
| `.anonymous-user-id` | 目录挂载覆盖不到；需文件 bind（宿主文件必须先存在）或改用 env |
| `.credentials.yaml` | 同上；且它是上游 DSH 管理的文件，路径不可轻易改 |
| `relay-token` | 可由 `ETERNA_RELAY_TOKEN` env 提供；否则仍是根级文件 |

文件 bind mount 的硬约束：**宿主文件必须预先存在**，否则 Docker 会在该路径建目录，
容器内 `cat /data/relay-token` 变 `EISDIR`。需要 `deploy/init-data-dirs.sh` 预先 `touch`，
或在 entrypoint 里把 relay token/凭据文件迁到目录内（涉及上游/Dockerfile 改动）。

- ✅ compose 一眼看清每个数据类；
- ✅ 可分盘/分权限（sessions 放 SSD、market 放 HDD）；
- ❌ 清单会随上游新增路径失效（例如 rc.5 新增 `office-kit/`、`dsh-runtimes/`、`cache/`）；
- ❌ 三个根文件要额外处理；
- ❌ 漏一行 = 静默落容器层，容器重建即丢。

### 4.3 方案 C（不推荐）：父子双挂

整树挂载 + 关键子目录再挂一次（`/data` 与 `/data/sessions` 同时 bind）。
技术上可行，但语义冗余、排障困难；只有「同一根内某子目录要换盘」时才有意义。

### 4.4 结论

- 默认 **A**；
- 需要分盘的用户显式启用 **B**，并在 entrypoint 加「每个清单路径必须是 mountpoint」的预检；
- C 仅在运维有明确分盘需求时作为 override 片段提供；
- **无论 A/B，`profiles` + `.pnpm-store` + `market` 必须同盘**（§1.4）。

### 4.5 文件系统前提：macOS Docker Desktop 的 FUSE 风险（必须先验证）

现网 named volume 在 Docker Desktop 的 VM 原生 ext4 上；改成宿主 bind 后，容器内看到的是
`fuseblk`（virtiofs/gRPC-FUSE）。SQLite WAL/-shm 依赖 POSIX 锁与 mmap，在部分
FUSE/网络文件系统上语义不完整，存在损坏或 `database is locked` 风险。

因此本方案增加一条**上线前置门禁**：

1. 先在独立测试实例（独立端口 + 独立数据根，不碰生产）完成迁移；
2. 注入并发读写（≥50 会话、持续 24h），每 2h 对
   `users.db`、`.eterna/*.sqlite3`、`workspaces/*/.eterna/*.sqlite3` 跑 `PRAGMA integrity_check`；
3. 观察容器日志有无 `SQLITE_BUSY`/`database is locked` 异常升高；
4. 全绿才迁生产；任一异常，走下面任一替代：
   - **A-alt**：DB 目录（`access/`、`.eterna/`、`storages/`、`sessions/`、`workspaces/`）
     继续用 named volume，其余绑宿主目录（混合，牺牲单一数据区目标）；
   - **A-linux**：把生产迁到 Linux/NAS Docker（本地 ext4/btrfs，非网络盘），整树 bind 安全；
   - **A-mac**：接受风险并加监控（不推荐）。

> 这一条不是理论洁癖：SQLite 损坏是**静默**的，等发现时备份可能已经覆盖。
> 在 macOS 宿主上，FUSE + WAL 必须用实测数据说话。

## 5. Compose / env 改造

### 5.1 新增变量

`.env`（生产）与 `.env.example`：

```dotenv
# 宿主专用数据区（默认 $HOME/eterna-data；写入 .env 时必须是绝对路径）
# 本机示例；部署脚本先 install -d -m 0700 "$ETERNA_DATA_ROOT"
ETERNA_DATA_ROOT="${ETERNA_DATA_ROOT:-$HOME/eterna-data}"
```

`docker-compose.yml`（base）：

```yaml
    volumes:
      - ${ETERNA_DATA_ROOT:?set ETERNA_DATA_ROOT}/base:/data
```

`docker-compose.super.yml`（super）：

```yaml
    volumes:
      - ${ETERNA_DATA_ROOT:?set ETERNA_DATA_ROOT}/super:/data
```

生产 `eterna-deploy/docker-compose.yml`（当前 super 形态）：

```yaml
    volumes:
      - ${ETERNA_DATA_ROOT:?set ETERNA_DATA_ROOT}/super:/data
```

同时删除：

```yaml
volumes:
  eterna-home:
    external: true
    name: agent-basis_eterna-home
```

> 注意：`compose` 的 `:?` 是 fail-closed 语法——变量缺席时 `up` 直接报错，
> 不会静默把数据写到仓库目录。这是本方案的安全底线。

### 5.2 为什么保留容器路径 `/data`

- `working_dir=/data`、`DSH_HOME=/data`、entrypoint 的 `$DSH_HOME/...`、
  审计/治理/记忆的 `$cwd/.eterna`、access 的 `$DSH_HOME/access/...` 全部按 `/data` 写死；
- 数据库/配置里可能存了绝对路径（workspaces、profile symlink 目标）；
- 改容器路径 = 全仓路径审计 + 数据迁移，收益为零。

**只换宿主源，不换容器目标。**

## 6. 配套代码/脚本改造（实施阶段才做）

### 6.1 entrypoint 持久化预检（必须）

在 `docker/entrypoint.sh` 启动早期加一段只读检查：

```sh
# 方案 A：/data 本身必须是 mountpoint
if ! awk '$2 == "/data" { found=1 } END { exit found ? 0 : 1 }' /proc/mounts; then
  echo "[entrypoint] FATAL /data 不是挂载点——数据会落容器层，拒启" >&2
  exit 1
fi
```

方案 B 则逐项检查 `$DSH_HOME/{profiles,sessions,storages,access,workspaces,...}`。

目的：把「漏挂」从静默数据丢失变成启动失败。这条预检在 named volume 下同样成立
（named volume 也是 mountpoint）。

### 6.2 `DSH_AGENTS_HOME`

上游 rc.5 使用 `$DSH_AGENTS_HOME`（默认 `~/.agents`）装载用户全局 `AGENTS.md` 与 user skills。
现网 `/root/.agents` 不存在，升级后用户一旦写入就会落容器层。

建议：

```yaml
environment:
  DSH_AGENTS_HOME: /data/agents
```

并在 init 脚本建 `${ROOT}/agents`。

### 6.3 relay token 与根级文件

方案 A 下 `/data/relay-token` 天然持久化，无需改动。

方案 B 下二选一：

1. 生产固定 `ETERNA_RELAY_TOKEN` env（令牌进 `.env`，已有支持）；
2. 改造 entrypoint：令牌文件改为 `$DSH_HOME/relay/token`，并挂 `${ROOT}/relay:/data/relay`。

`.credentials.yaml` / `.anonymous-user-id` 属上游 DSH 管理文件，方案 B 下需要：
文件预创建 + 单独文件 bind，或接受「父目录兜底」——这也是 B 不如 A 的原因。

### 6.4 宿主初始化脚本（新增 `deploy/init-data-dirs.sh`）

职责：

- 默认根 `ETERNA_DATA_ROOT="${ETERNA_DATA_ROOT:-$HOME/eterna-data}"`；
  `install -d -m 0700 "$ETERNA_DATA_ROOT"`；
- `mkdir -p` 方案 A/B 的实例子目录；`chmod 700` 根；`touch` 方案 B 的三个根文件；
- 打印最终树，供人工核对；
- 不写任何密钥内容；不把根目录纳入 git。

### 6.5 备份脚本（建议新增 `deploy/backup-data.sh`）

- 默认冷备：`docker compose stop` → `tar czf` → `start`；
- 热备只做 `rsync --exclude=.pnpm-store`，并明确 SQLite WAL 风险；
- 备份文件放 `${ETERNA_DATA_ROOT}/backups`，再同步到第二块盘/NAS（可选）。

### 8.1 备份策略

## 9. 权限与安全

| 项 | 要求 |
|---|---|
| 宿主根 | `0700`，属主为运行 Docker 的用户/root |
| 敏感文件 | `access/secret.key`（现 0600）、`companion-tokens.json`（0600）、`.credentials.yaml`（0600）、`relay-token`（0600）保持 0600；`users.db` 实测 0644，需评估收紧 |
| `.env` | 不进数据根；留在部署目录，`0600`，备份单独加密 |
| 备份 | 含全部敏感面，视同密钥；传输加密、落盘加密 |
| 网络文件系统 | 禁止（SQLite WAL/flock 不可靠） |
| macOS Docker Desktop | bind 为 virtiofs/gRPC-FUSE：容器内 `chmod/chown` 不落宿主，0600 语义可能失效；按 §4.5 先验证 |
| Linux | 容器 root 会在宿主产生 root 属主文件；运维账号用 sudo/ACL 读取 |
| 硬链接 | `profiles` + `.pnpm-store` + `market` 必须同文件系统（§1.4） |
| 大小写 | 宿主 APFS 默认大小写不敏感；用户文件名 `README`/`readme` 并存会冲突 |
