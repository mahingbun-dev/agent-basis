# 25 - 业界架构对照与缺陷清单（superagent 式任务内核的多智能体风险）

> 状态：**调研沉淀**。本文以一手文献为依据，对照本仓拟移植的 superagent 式任务内核，列出架构卡点与专家解法。
> 用途：`24` 号融合设计的**外部依据**；评审时回答"为什么这样改"。
> 关联：`24-主动工作体系融合设计-任务内核与chat-demo范式.md`、`08-基座插件体系与总体架构.md`、`09-RSI自进化机制设计.md`、`07-评测体系-ai-evo对接与本地eval插件.md`
> 调研日期：2026-11-16

---

## 0. 一句话结论

**superagent 的领域模型（Object Model）处于业界第一梯队，但其运行时工程与验证机制存在明显缺口**——而这些缺口恰好对应本仓已有的强项（预算守卫、G0/G1/G2 门禁、审计留痕）。移植时应"取其模型、补其运行时"。

同时必须承认：**"多智能体天然更优"已被实证证伪**。Anthropic 实测多智能体系统消耗约 **15 倍** chat 的 token（单 agent 约 4 倍），在 BrowseComp 上 **token 用量解释了 80% 的性能方差**。所谓"更好"很大程度是"**烧更多 token**"。

## 1. 业界分歧地图（四派）

结论互相矛盾，必须先分辨学派再引用：

| 学派 | 代表文献 | 核心主张 | 对 superagent 的判决 |
|---|---|---|---|
| **反多智能体派** | Cognition《Don't Build Multi-Agents》 | 两条原则：① 共享完整上下文与轨迹 ② 动作携带隐式决策。违反者应被"默认排除" | 结构上**触碰两条线** |
| **有条件支持派** | Anthropic《Building Effective Agents》 | 五种工作流模式；先找最简方案，agent 仅在需要灵活决策时使用 | 属 orchestrator-workers，**场景用对了** |
| **实证量化派** | MAST《Why Do Multi-Agent LLM Systems Fail》(arXiv 2503.13657) | 14 种失败模式、3 大类；多数系统性能增益"often minimal" | 提供**缺陷检查表** |
| **工程还原派** | 12-Factor Agents、Temporal、A2A | agent 就是软件：自己拥有 context 与 control flow；人机接触建模为工具调用；任务需持久状态机 | superagent **大体符合**，个别落后 |

### 1.1 MAST 分类（可直接当检查表）

**类别一：规范与系统设计（5 种）**
- FM-1.1 不遵守任务规范 · FM-1.2 不遵守角色规范 · FM-1.3 步骤重复 · FM-1.4 丢失对话历史 · FM-1.5 不知道终止条件

**类别二：智能体间失配（6 种）**
- FM-2.1 对话重置 · FM-2.2 未请求澄清 · FM-2.3 任务偏离 · FM-2.4 信息隐瞒 · FM-2.5 忽略他者输入 · FM-2.6 推理与行动不一致

**类别三：任务验证与终止（3 种）**
- FM-3.1 过早终止 · FM-3.2 无验证或验证不完整 · FM-3.3 验证不正确

**方法论可信度**：150 条 trace 人工标注，标注者一致性 **κ = 0.88**；MAST-Data 覆盖 7 个主流 MAS 框架、1600+ 条标注 trace。

**论文的重要保留**：修复干预效果**混合**——ChatDev 经拓扑改动后 ProgramDev 从 25.0→40.6，但 AG2 在 GPT-4 下拓扑改动不显著（p=0.4）。作者结论：现有修法"**不能解决全部失败案例**"，需更复杂的结构性方案；并把 MAS 失败框定为**组织设计缺陷**而非纯粹的模型能力局限。

## 2. 九个卡点：现象 → 证据 → 专家解法

### 卡点 1｜上下文与成本的复合爆炸（最严重）

**现象**：主 Session 常驻接收候选卡/worker 报告/followup；每工单一个 worker Session；worker 再开子代理。三层嵌套。

**证据（已核实代码）**：
- 主 Session 候选卡文本截断 4000 字符、线程窗口 5+5 条、其余消息仅 50 字符预览 → **是缓解，不是解决**；
- `grep` 全仓：**无任何主动成本上限**。仅有 `src/app/retry-health.ts` 事后观测 `budget_exceeded` 错误——"撞墙了才知道"；
- `maxWorkers` 限制的是**并发槽**，不是 token 预算。

**专家解法**：
- Anthropic **effort scaling**：简单查询 1 agent / 3–10 次工具调用；比较类 2–4 个 subagent；复杂研究 10+（写进 prompt）；
- LangGraph **双层持久化**：thread 级 checkpoint（短期）+ store（跨 thread 长期）——上下文与记忆分开管；
- Cognition **compression model**：把动作/对话历史蒸馏为"关键事实、事件、决策"。

**对本仓的启示**：**主 Session 必须挂预算守卫**（`governance/budget.ts` 的 maxTurns/maxTokens/maxCost + `agent/turn-stopping`）。这是移植时必须补的第一件事。

---

### 卡点 2｜验证靠自我声明，缺外部 oracle（MAST 头号杀手）

**现象**：worker 报 `ready` 的判定依据是 prompt 纪律——`prompts/work.md:49`："ready means reviewed implementation with relevant checks passed"。

这是 **FM-3.2（无验证/验证不完整）与 FM-3.3（验证不正确）的教科书样本**：模型自述"我检查过了"，无任何独立判定。

**专家解法（按强度排序）**：
1. **MAST Table 3**：*comprehensive verification & unit test generation*（结构性方案，非 prompt）；
2. **Anthropic evaluator-optimizer**：一模型生成、另一模型专门批判——适用于"有明确评价标准"的场景；
3. **Anthropic C 编译器项目的做法最有说服力**：测试当 oracle、CI 强制、甚至**用 GCC 当"在线已知良好编译器"做差分判定**；其明确警告——"**很容易看到测试通过就以为完工，而这几乎从不是真的**"。

**对本仓的启示**：`ready` 必须**过门禁才成立**——本仓已有 **G1 本地 eval replay（30 条金集）+ G2** 正是答案。把"ready = 金集通过"写进 Mandate 执行契约，让报告状态由系统判定而非 worker 自述。**这是移植中价值最高的一处改造。**

---

### 卡点 3｜跨 worker 上下文不共享（Cognition 的核心指控）

**现象**：一工单一个 worker Session + 独立目录；worker A 改接口，worker B 看不见。

**证据**：`src/executor/dsh.ts` 的 `workerSessionId(ticket.id)` + 独立 workspace 目录；worker 间通信靠主 Session 打字转述（`inputMessage` / `reportRelay`）。

**专家解法**：
- Cognition：subagent 无法共享隐式决策 → **要么单线程线性，要么别做**；Flappy Bird 例（一个做马里奥背景、一个做不搭的鸟，合成失败）；
- Anthropic 实测缓解：**subagent 输出落文件系统**，避免"game of telephone"——superagent 的 `orchestrator_read` 部分对上；
- **Claude Code 最务实**：subagent **顺序执行**、**通常只回答问题不做改动**，存在目的是"把调查性工作挡在主历史之外"。

**对本仓的启示**：worker 分工延续**单仓库单目录**（不跨目录并行改共享代码）；worker 干活、调查类子任务才并行；跨工单共享靠**工作区文件 + 知识库**，不靠消息转述。

---

### 卡点 4｜任务分解质量全依赖 orchestrator 的 prompt

**Anthropic 的实测失败案例（逐条对照）**：
- **过度生成**："为简单查询创建 50 个 subagent"；
- **重复劳动**：模糊委派 "research the semiconductor shortage" → 一个查 2021 芯片危机、两个重复查当前供应链；
- **过程缺口**：弱任务描述导致"重复、留缺口、找不到必要信息"；
- **搜索习惯差**：查询过长过窄，返回极少结果。

**专家解法**：每个委派必须给 **objective / output format / tool guidance / task boundaries** 四要素，配合 effort scaling。superagent 的 `prompts/dispatch.md` 有路由细则但**无 effort 分级、无四要素硬约束**。

**对本仓的启示**：候选卡强制携带四要素，否则 Eval 拒绝；给主 Session 引入 `delegation_effort` 档位（简单/比较/复杂），直接对齐 Anthropic 的量化建议。

---

### 卡点 5｜自建 mini-Temporal 的成熟度差距

**现象**：`app/effects.ts`（6 种 kind + 独立退避）+ `app/outbox.ts`（回执）+ `store.ts`（SQLite + 目录锁）。设计水准高，但这是**从零手写持久执行引擎**。

| Temporal 提供 | superagent 现状 |
|---|---|
| **确定性重放**（event history 回放重建状态） | ❌ 无；靠 `assignmentInterrupted` + effect 行恢复 |
| Activity 重试/超时/心跳由平台配置 | ✅ 自建，6 种 kind 各有策略 |
| Signal / Query / Update（运行中干预） | ✅ 部分（note / requestStatus） |
| **Worker Versioning**（升级不打断在跑的 agent） | ❌ 无 |
| 崩溃后"在哪停就从哪继续" | ⚠️ 只恢复排队副作用，不能重放整个 turn |

Temporal 明确列出的它消灭的失败模式——"crash 或重新部署时丢失 in-flight 状态，导致要自己维护状态表、检查点、对账作业"——**正是 superagent 正在自建的那套东西**。

**对本仓的启示**：移植时**不要重写这套**。先评估 DSH 宿主的持久能力（`tool-jobs` / `schedule` / session persistence 已开），再用本仓 SQLite 惯例承接。**"自己能写"不等于"应该自己写"。**

---

### 卡点 6｜单写者 Engine 的可扩展性边界（对本仓最关键）

**现象**：Engine 全同步方法、每命令一事务、SQLite 单文件 + `proper-lockfile` 目录锁。

这是**刻意的简洁**（哲学正确：单一事务写入者），代价明确：
- 天然**单机单进程**；
- 本仓要的**多租户 realm 维度没有位置放**；
- 横向扩展无路径。

**专家解法**：
- 12-Factor #5「**统一执行状态与业务状态**」+ #12「**agent 是无状态 reducer**」——状态全推给存储，计算无状态；
- LangGraph：`thread_id` 是连续性单位，存储可换 Postgres/SQLite，生产必须持久后端；
- 本仓的现成选择：**一租户一 SQLite**（改动小、隔离硬）或 Postgres + 行级 realm 过滤。

**对本仓的启示**：支持 `24` 号 §9 待拍板第 3 项——**realm 进模型**（对齐 12-Factor #5，不变量硬）**优先于**外层过滤（改动小但可绕过）。

---

### 卡点 7｜人机交互语义与 A2A 标准相反（取舍非缺陷）

| | superagent | A2A 规范 |
|---|---|---|
| 等人输入 | Attention（仅在 blocked 时结构化提问） | `INPUT_REQUIRED`（一等状态） |
| 恢复方式 | 人的消息落在线程 → **可恢复已结束工单** | 同 `taskId`+`contextId` 续；**终态后拒绝任何消息**（`UnsupportedOperationError`） |
| 终态数 | 6 种报告 + open/ended | 4 个终态：COMPLETED / FAILED / CANCELED / REJECTED |
| 中断态 | 无显式状态（`idle` = 回合结束） | 显式 `INPUT_REQUIRED` / `AUTH_REQUIRED` |

**A2A 关键规则**（供对接参考）：终态后不再接受消息、流关闭、拒绝订阅、取消返回 `TaskNotCancelableError`；取消**幂等**；`input_required` 时客户端用**同 `taskId` + `contextId`** 续接同一任务而非新建；`referenceTaskIds` 可引用相关任务。

**对本仓的启示**：企业内要接异构系统，**把 Attention 显式化为可映射到 A2A `input-required` 的状态**是低成本高回报。反过来说，superagent 的"讨论可恢复已结束工单"**比 A2A 更贴合真实协作**（客户追问常发生在"结案"之后），应保留、不向标准妥协。

---

### 卡点 8｜可观测性缺一层：没有决策轨迹

**现象**：有 health board、panel、prompt 版本绑定（每次请求记录所用品本）——**但没有 per-turn 决策轨迹**。

**专家共识**（Hamel《Your AI Product Needs Evals》）：
- **trace logging 是人审与模型审的前提**；要点是"移除看数据的所有摩擦"；
- 先做**二元好坏标注**，别急着做细粒度评分；
- 端到端评测难，因为**正确性常是主观的**，且模型评审本身需要被评测（"a meta-problem within your larger problem"）；
- 失败类别不均衡时原始一致性会误导，应**分别测 precision 与 recall**；
- 小 eval 集**不要求 100% 通过**——通过率是**产品决策**；测试应从真实失败中持续更新，并"难到模型难以通过"以暴露可修弱点。

**Anthropic 的坦白**：长时有状态 agent **错误会累积、行为非确定性、调试极难**，靠 tracing + rainbow deployment 缓解。

**对本仓的启示**：接上 **audit NDJSON**——把 audit 从"合规留痕"升级为"调试 trace"：一条工单的 Trigger → 候选卡 → Decision 理由 → 委派四要素 → 报告 → 门禁结果，全部可查。**一份数据两种用途**，移植时最省力的收益。

---

### 卡点 9｜主动性的默认失败模式是"话太多"

**superagent 做对的**：`inferred` 必须先走观察模式；准入矩阵三格；philosophy 明言"发现它吵，就把 prompt 改短改严或暂停，而不是加更多消息去解释吵闹"。

**但业界默认失败是过度生成**（Anthropic 的 50 个 subagent 案例）。MAST 的 FM-1.5「不知道终止条件」+ FM-3.1「过早终止」是这类问题的两面。

**对本仓的启示**：三道保险（准入矩阵 + 观察模式 + 红线）正确，**再加一道**：`inferred` 放量前必须**量化误报率**（`24` 号定为 < 10%），并对"主动产生的工作"**单独计成本**——因为它花的是**别人的注意力**。这是 superagent philosophy 中唯一提到"责任"的部分。

## 3. 专家共识 vs 已被证伪

### 3.1 已被证伪（别再照着做）

| 观点 | 证伪依据 |
|---|---|
| 多智能体天然优于单 agent | MAST：性能增益"often minimal" |
| 让 agent 互相对话来消除冲突 | Cognition：2025 年 agent 还不能可靠长上下文主动对话，"决策制定太分散" |
| 用框架解决架构问题 | Anthropic：生产要**剥掉抽象层**、理解底层代码 |
| 更复杂的架构 = 更好 | Anthropic："成功是找对的系统，不是最复杂的系统" |

### 3.2 已成为共识（可直接采纳）

| 共识 | 出处 |
|---|---|
| **Context 归你自己拥有** | 12-Factor #3 · Cognition 原则 1 |
| **Control flow 归你自己拥有**（LLM 只选下一步，代码管流程） | 12-Factor #8 |
| **人机接触建模为工具调用** | 12-Factor #7 · superagent 的 `human_action` 结构化字段 |
| **工具是结构化输出**（schema 即 API 面） | 12-Factor #4 · superagent 的 zod `.strict()` |
| **执行状态与业务状态统一；agent 是无状态 reducer** | 12-Factor #5 / #12 |
| **早期就要小而不完整的 eval 集**（~20 条起步） | Anthropic · Hamel |
| **降级优先**：先最简方案再加复杂度 | Anthropic |
| **错误要压缩后再回灌**（不要塞原始错误） | 12-Factor #9 |
| **小而专注的 agent** | 12-Factor #10 |
| **从任意渠道触发，去用户所在的地方** | 12-Factor #11 |

### 3.3 12-Factor Agents 完整清单（对照用）

1. 自然语言转工具调用 2. 拥有你的 prompts 3. 拥有你的 context window 4. 工具即结构化输出 5. 统一执行状态与业务状态 6. 用简单 API 支持启动/暂停/恢复 7. 用工具调用接触人 8. 拥有你的控制流 9. 把错误压缩进上下文 10. 小而专注的 agent 11. 从任意位置触发 12. 让 agent 成为无状态 reducer（附录 13：预取所有可能需要的上下文）

## 5. 对 24 号融合设计的 6 条修订

以下修订改变 P1 的**实施契约**，不改变路线顺序：

| # | 修订 | 对应卡点 | 落点 |
|---|---|---|---|
| **R1** | **主 Session 预算守卫**：effort scaling 分级 + maxTokens/maxCost 硬截断 | 卡点 1 | 接 `governance/budget.ts` + `agent/turn-stopping` |
| **R2** | **`ready` 必须过门禁**：由系统判定（G1 金集 replay），worker 自述作废 | 卡点 2 | Mandate 执行契约 + `evolve/gates.ts` |
| **R3** | **委派四要素硬约束**：候选卡必须带 objective / output format / tool guidance / task boundaries，否则 Eval 拒绝 | 卡点 4 | `packages/tasks` 的 Eval/候选卡 |
| **R4** | **worker 输出落文件系统**：`.ticket/<id>/` 下写 progress/决策/evidence，主 Session 读文件而非读消息 | 卡点 3 | executor 适配器 + `orchestrator_read` |
| **R5** | **Attention 显式化**：可映射 A2A `input-required`；但保留"讨论可恢复已结束工单" | 卡点 7 | `interact` + tasks 状态机 |
| **R6** | **不重写持久执行引擎**：评估 DSH 宿主能力 + 本仓 SQLite 惯例；Temporal 失败模式清单当 checklist | 卡点 5 | P1 范围收缩 |

附加确认：**audit 升级为调试 trace**（一份数据两用），优于新建 trace 系统（卡点 8）。

## 6. 业界也未解决的四个真问题

诚实记录，避免过度承诺：

1. **跨 agent 的隐式决策冲突**——Cognition 长期看好但当前无解；superagent 用"单目录 + 主 Session 转述"绕开，不是解决。
2. **长时任务的错误累积与过程漂移**——Anthropic 承认调试极难；本仓 G 门禁能兜"产出质量"，兜不住"过程漂移"。
3. **成本不可预测**——15× token 是结构性的，effort scaling 只是缓解。企业采购需要"每工单成本上限"的产品承诺，业界尚无成熟做法。
4. **验证的语义边界**——金集能测"已知场景"，测不出"新场景是否做对"；MAST 建议的 unit test generation 在非编码场景难以直接迁移。
