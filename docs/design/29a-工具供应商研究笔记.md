### 对 29 号 §5 的回填建议

**可标已核实**：
- §5-R1 全部三项研读项：① web_search 工具参数形态（声明方式 13 子字段 + 顶层回流格式）② 文件上传接口（四操作 + 独立 parser 体系）③ 语音端点（ASR/TTS/音色管理/Realtime）。
- 附带核实 §5-R5 智谱部分：web_search 有独立 API（`/paas/v4/web_search`），read_url 有独立端点（`/paas/v4/reader`），文件解析/ASR/TTS 亦全部独立 REST——五能力无一是「只能走 chat」的形态。

**仍 open（实现期验证）**：本节 unresolved ①–⑥，重点：流式模式下 web_search 来源数组回流位置（①，glm 适配器首轮真调验证，可挂 llm-doctor 逐能力探活）。

**对 29 号其他节的修正**：
- §2.4 借用机制：GLM 出借能力可**零 token**——直接打 `/paas/v4/web_search`、`/paas/v4/reader` 等独立端点（Bearer 鉴权，搜索按次计费），不必构造 chat 请求；原拍板「借用消耗出借方一次小额模型调用」对智谱出借方不成立。
- §4 P-2 glm 适配器：契约参数（引擎/条数/域名/时效/摘要长度）与 `tools[].web_search` 子字段几乎 1:1 映射；非流式从响应顶层 `web_search[]` 取来源卡（refer↔角标），流式按「chunk 无 web_search 字段」设计。
- §7-2 语音供给链：TTS PCM 24kHz SSE 与 chat-demo 管线同构；ASR 为整文件（≤30s）multipart——长音频需自托管栈补位，与 R7 拍板一致。

### unresolved（原笔记照录）

1. 流式（SSE）模式下 web_search 来源数组的确切回流位置：OpenAPI 规范的 ChatCompletionChunk 中无 web_search 字段，且联网搜索指南的非流式响应示例（search_result=true）也未展示顶层 web_search 数组——规范与示例文本不完全一致。无 API key 未实测；glm 适配器实现时需以最小真调验证（可挂到 llm-doctor 逐能力探活）。
2. TTS 指南页调用示例的 voice="female" 与 API 规范枚举（tongtong/chuichui/xiaochen/jam/kazi/douji/luodo）不一致，指南示例疑为旧文案；未实测，以规范枚举为准。
3. 文件上传 purpose：字段描述提及 user_data（pptx/ppt/docx/doc/xlsx/xls/pdf，1T/用户），但 schema enum 与列表接口 enum 均未含它；实际可传性未验证。
4. ASR/TTS 及各搜索引擎的具体计价数字：搜索四档价格已从指南核实；语音与 ASR 单价文档指向 bigmodel.cn/pricing 价格页，本次未抓取核实（非任务必查项）。
5. `/paas/v4/voice/delete` 与 `/paas/v4/files/parser/create`（异步解析）+ `/result/{taskId}/{format_type}` 仅从 sitemap/路径确认存在，未逐字段展开请求响应 schema。
6. 无独立 WebSocket ASR 端点的结论基于 sitemap+实时 API 页全量核对（实时语音走 GLM-Realtime WSS，非纯转写）；「不存在」类否定性结论受限于文档公开面，如有未公开端点则无法覆盖。

## R3 OpenAI 兼容 function calling 最大公约数（→ 回填 §5-R3，generic 兜底协议底座）

方法声明：以 `openai/openai-openapi` 官方 OpenAPI 规格 v2.3.0（GitHub raw，4,323,310 字节，curl 下载后 python/yaml 逐 schema 抽取）与 developers.openai.com 官方指南（function-calling / streaming）为据；platform.openai.com 旧域 WebFetch 返回 403 未取得。未做真实 API 请求。

### 结论表（协议环节 × 标准形态 × 来源 URL）

| 协议环节 | Chat Completions 标准形态（最大公约数） | 来源 URL |
|---|---|---|
| 工具定义（发送侧） | `tools[]` 四件套 `{type:"function", function:{name, description, parameters}}`；name 保守约束 `^[a-zA-Z0-9_-]+$` 且 **≤64**（Chat 轨道规格 ≤64 与 Responses 轨道 ≤128 的交集）；`parameters` 为 JSON Schema object，省略=空参数，schema 用朴素子集（type/properties/required/enum/description/嵌套 object）；**不发送** `strict`（Structured Outputs 特有，不合规请求会被拒）、`custom` 工具、`allowed_tools`、`namespace`、`defer_loading`——均为 OpenAI 特有，跨供应商无契约；旧参数 `functions`/`function_call` 规格已标 deprecated，禁用 | https://raw.githubusercontent.com/openai/openai-openapi/master/openapi.yaml ； https://developers.openai.com/api/docs/guides/function-calling |

| 结果回灌（下一轮请求） | 官方固定序列：先 push 含原样 `tool_calls` 的 assistant 消息，再**每个 tool_call 一条** `{role:"tool", tool_call_id:<id>, content:<string>}`；content 规格允许 string 或 text parts 数组，**generic 保守用 string**（JSON 序列化/纯文本/错误描述）；结果格式自由（JSON/error/plain text），失败/降级也显式回灌字符串而非留空——与 29 号 §5 降级语义「显式表达」直接对齐；带同一 `tools` 声明再次请求，循环直至 `finish_reason!="tool_calls"` | 同上 |

| Responses 轨道对照（不进公共子集） | 平铺 tool 定义（name ≤128）；模型调用输出项 `{type:"function_call", id:"fc_…", call_id:"call_…", …}`——**双 ID：回灌用 call_id 不是 id**；回灌项 `{type:"function_call_output", call_id, output}`；流式为语义事件（response.output_item.added → function_call_arguments.delta → done）；推理模型 reasoning items 须随工具输出回传（仅此轨道官方明文） | https://raw.githubusercontent.com/openai/openai-openapi/master/openapi.yaml ； https://developers.openai.com/api/docs/guides/function-calling |
| 轨道选择（分析判断） | generic 底座锚定 **Chat Completions 而非 Responses**：① 它是历史上所有「OpenAI 兼容」供应商事实模仿的接口面（本仓 `packages/llm-openai` 即此层）② Responses 独有概念（语义流事件/reasoning items/previous_response_id）无跨供应商先例 ③ Chat Completions 字段级契约在规格中完备（官方指南明言 GPT-6 系新模型仅 Responses 支持工具调用，Chat Completions 为兼容/传统定位但仍是文档化公开协议） | 同上（分析结论，非官方陈述） |
| 成本口径 | 工具定义注入 system 位并**计输入 token**（指南 Token Usage 节）；官方软建议单轮初始函数 **<20 个**——影响 29 号 §7-1 搜索链 token 预算与 toolkit 工具包大小设计 | https://developers.openai.com/api/docs/guides/function-calling |

### 对 29 号 §5 的回填建议

**可标已核实**：§5-R7 全部三项：① 部署面（FunASR 四类容器路径含 compose+OpenAI 兼容；CosyVoice 自建 GPU 镜像/triton_trtllm compose，无官方预构建镜像）② 延迟与并发基线（官方 benchmark 数字 + 「绑定硬件禁止当通用承诺」口径）③ 替代选型对照（ASR/TTS 各候选官方数字与缺口）。

**仍 open**：本节 unresolved 7 条（openai_http 服务无官方基准、C++ WS 无首字延迟实测、runtime/python 无基准、150ms 查无 CV2 原文、GPT-SoVITS/IndexTTS 缺口、24kHz 未从模型卡核实、C++ 镜像版本两处不一致）。

**对 29 号其他节的修正（§4 P-3 落地推论）**：
1. compose 服务形态：ASR 直接采用官方 `examples/openai_api/docker-compose.yml`；TTS 用 runtime/python Dockerfile 自建（GPU）或 triton_trtllm compose（GPU 生产）——**两者都不是「拉镜像即用」**，镜像构建/预热时间计入部署脚本。
2. §3 doctor 探活：FunASR OpenAI API 有 `/health`（官方警告健康≠转写正确）；CosyVoice fastapi/grpc **无 health 端点**——语音适配器要为两种探活语义留接口（HTTP health vs TCP/推理级探测）。
3. PCM 契约：FunASR ws 入 8k/16k PCM，CosyVoice 出裸 int16 PCM（CosyVoice2 24kHz）——chat-demo 的 PCM 24kHz 单一格式在自托管侧不成立，**适配层需固定「重采样责任方」（24k→16k 下采样）**。
4. 容量口径：上线前按 `rtf_reproducibility.md` 必填字段（数据/模型/运行时/硬件/软件/pipeline/批处理/计时范围/质量）自测基线——与本仓「金集/doctor 真测」纪律一致。
5. 鉴权：两个栈官方服务面均无鉴权（FunASR 明示、CosyVoice CORS 全开）——compose 内网部署 + 网关收口是硬前提（与 §6 governance egress 白名单同理）。

### unresolved（原笔记照录）

1. FunASR OpenAI 兼容 HTTP 服务（examples/openai_api 与打包 funasr-server）本身无官方延迟/并发基准数字：官方文档明示需按 rtf_reproducibility.md 字段自测，funasr.com 部署中心 vLLM 路径亦注记「8 个 HTTP 请求均为功能验证…不代表容量」。

## 附-A：§5-R5 独立端点问题的分布式答案（R5 无独立笔记，由 R1/R2/R4 附带覆盖）

29 号 §5-R5 原文：「是否存在**独立**搜索 / 语音端点（决定借用是否必须走完整 chat 侧调用）：智谱 web_search 独立 API？MiMo-Audio 端点形态？DeepSeek 搜索是否只能经 messages API」。三个子问题的答案：

| R5 子问题 | 答案 | 依据 | 细节 |
|---|---|---|---|
| 智谱 web_search 独立 API？ | **存在** | R1 | `POST /paas/v4/web_search`；且 read_url（`/paas/v4/reader`）、文件解析（`/paas/v4/files/parser/sync`）、ASR（`/paas/v4/audio/transcriptions`）、TTS（`/paas/v4/audio/speech`）**五能力全部有独立 REST 端点**，统一 Bearer 鉴权——GLM 出借能力零 token、零 chat 请求 |
| MiMo-Audio 端点形态？ | **无独立端点** | R2 | ASR/TTS 全部复用 `POST /v1/chat/completions`，仅以 model 区分（mimo-v2.5-asr / mimo-v2.5-tts*）；web_search 亦无独立搜索端点（chat tools 声明）——借用 = 一次最小 chat 请求（专用 model id + 单条消息），无需完整对话 |
| DeepSeek 搜索是否只能经 messages API？ | **否** | R4 | `POST /v1/tools/search`、`POST /v1/tools/fetch` 独立 REST（¥5/1000 次；Search 100 QPS / Fetch 25 QPS）；ASR/TTS 亦独立（`/v1/tools/asr`、`/v1/tools/tts`，与对话模型无关） |

**对 §2.4 的合并修正**：三家中 GLM 与 DeepSeek 出借能力可直调独立端点（按次计费、无 token 成本）；MiMo 是唯一需要构造 chat 形态请求的出借方。原拍板句「借用消耗出借方一次小额模型调用」建议改写为：「借用消耗出借方一次**能力侧调用**——独立端点直调（GLM/DeepSeek，按次计费）或最小 chat 请求（MiMo，计 token）」。
