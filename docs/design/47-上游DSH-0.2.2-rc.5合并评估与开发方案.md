## 0. 执行摘要

### 0.1 三个必须先说清的事实

1. **本仓库不是上游 fork。** 两仓无共同 git 历史（`git merge-base` 不存在），所以
   「合并上游」不是 `git merge upstream/master`，而是三层工作：
   - **L1 依赖族升级**：`@deepseek-ai/dsh-*` / cordis 从当前钉版升到目标版；
   - **L2 上游派生文件重放**：profile/preset 模板、skills、compaction fork、cordis vendor；
   - **L3 上游新能力选择性采纳**：按产品边界逐项决策。
2. **目标版本是 `0.2.2-rc.5`**（上游 tag `dsh-v0.2.2-rc.5`，2026-11-18）。
   npm 事实：`latest = 0.2.2-rc.1`，`next = 0.2.2-rc.5`——**rc.5 是预发布通道**。
   `docs/upgrade-gate.md` §7 原为「rc 不上生产」；**2026-11-19 产品拍板 rc.5 上生产**，
   该节已改为「默认禁预发布 + 本次书面例外 + 全门禁/回滚条件」，不再是待决项。
3. **现仓版本面自相矛盾**，升级前必须先收敛：
   | 位置 | 现值 |
   |---|---|
   | `pnpm-workspace.yaml` catalog（20 个 `dsh-*` + cordis/cosmokit/schemastery） | `0.2.2-alpha.2` / cordis `4.0.6-alpha.1` / cosmokit `~1.8.7-alpha.1` |
   | 根 `package.json` devDependencies | `0.2.2-rc.1`；`engines.node` 仍 `>=22` |
   | `Dockerfile:2,50` 全局内核 + mcp-client | `0.2.2-alpha.3` |
   | `packages/llm-openai` | `0.2.2-rc.1`（其 cordis/loader/cosmokit 已是 4.1.0/1.1.0/1.9.0） |
   | `tools/evals`、`packs/*`、`market/*`、`basis/basis-minimal` | `alpha.2` / `rc.1` 混用 |
   | `audit/extra/governance` 的 loader/include | `~1.0.7-alpha.1` / `~1.0.11-alpha.1` |
   | 生产容器实际内核 | `0.2.2-alpha.3` |

   **额外事实**：`node_modules` 里实际运行的 cordis 已是 **4.1.0**（rc.1 的 dsh-compaction 等包
   peer 为 `~4.1.0` 拉入），而 catalog 还钉 `4.0.6-alpha.1`。把 catalog 抬到 4.1.0
   是**修现状**，不是引入新风险；但 `core/cordis` 另有一份 4.0.6 vendor，见 §2.7。

### 0.4 推荐路线（一句话）

**直接升 rc.5（P0-2 已拍板，不设 rc.1 检查点）；profile/preset 重放、v1 线合并、锚点同步

作为唯一回滚点（不再有 rc.1 中间点）。P0-6 的干净 worktree 与 `origin/main` 基线保证

### 2.11 chat-import：能力与多租户错位（H10）

上游事实（rc.5）：

- 可选 bundle `@deepseek-ai/dsh-deepseek-chat-import`，`cordis.patch.yml` 只有一行
  `insert: deepseek-chat-import`；随 `dsh` 安装包提供，**默认关闭**；
- 浏览器半边通过 `sidebar.session.action` HOC 包裹“新建会话”行，追加一个上传按钮；
  不能导入的 Peer 原样返回 `children`；
- 上传路由 `POST /api/deepseek-chat-import/archive?workspaceId=…`，要求
  `application/octet-stream`，NDJSON 流式应答；整包在 Host 内存中，单 import 槽位；
- 默认限额：`maxSessions=1000`、`maxUploadBytes=512 MiB`、`maxEntryBytes=256 MiB`、
  `maxTitleBytes=80`；重复导入产生重复会话；损坏包可能已部分写入；合成文件卡片没有字节；
- 资格判定是 `principalOf(ctx.invocation) !== undefined` → 拒绝；`principalOf` 对
  `kind:'owner'` 返回 `undefined`。因此只有 owner Peer 能导入。

本品错位（H10）：

1. **unary HTTP 通道恒为 owner Peer**（`access/src/mux.ts` 头注），所以所有登录用户
   都会通过上游 owner 检查——这不是“仅管理员”，而是“没有租户校验”；
2. 路由里的 `workspaceRegistry.get(workspaceId)` 是全局注册表，**没有 workspaceOwner
   校验**；猜到他人 workspaceId 就能把会话写进他人工作区；
3. 导入直接写 `sessionPersistence`，绕过 `/api/session/create` 的
   `store.recordSession` → 导入会话在 access 账本里**没有 owner**，mux 的 session
   资源绑定、终端、文件面板、审批/提问桥都会把它当成“无主会话”。

产品化前提（B16 设计，缺一不可）：

- 在 access 的 `admit` 请求级入口拦截 `/api/deepseek-chat-import/archive`：
  cookie → `eterna-user`，校验 `workspaceId` 的 `workspaceOwner === userId`，
  否则 403；无 cookie 401；
- 保持流式，不缓冲 512MiB；成功后解析 NDJSON 的 `outcome.sessionIds`，
  逐条 `store.recordSession(sessionId, userId, workspaceId)`；失败/取消时用
  `workspaceRegistry.sessionIds` 对工作区做一次对账，把未记账会话补给 workspace owner
  （workspace 单属主，安全）；
- 审计 `chat.import`（userId/workspaceId/结果/会话数，**不记压缩包内容/标题**）；
- 内存风险：整包在内存中 + fflate 同步解压；容器无 mem limit 时先按 512MiB 默认跑
  浸泡，若 OOM 再评估下调 `maxUploadBytes`（只能下调，不得调大）；
- UI 先按上游按钮/对话框接入，做 v4 令牌/圆角/字重审计；审计不过则保留 Host 导入链、
  用产品自有 client 半边替换按钮与对话框（不得改上游源码）。

### 2.12 ACP：自动化 stdio 面，不是 Web 功能

上游事实（rc.5）：

- `@deepseek-ai/dsh-acp`：仅自动化的 ACP v1 服务器，JSON-RPC **stdio**；
  支持 `session/new/list/resume/close/prompt/cancel/config`、MCP stdio/HTTP、
  model/reasoning_effort；没有 UI、计划、终端、命令面；不支持删除/fork/回放；
- `@deepseek-ai/dsh-acp-app`：`acp` profile 组合包 = `dsh-base` + 本包；patch 设
  coding-agent persona、默认 `deepseek-official` / `deepseek-v4-flash`、禁
  `session-title-llm`、禁 HMR；**stdout 只留给换行 JSON-RPC 帧**；
- 客户端是受信控制器；会话可跨进程 `session/list`/`resume`；同一 profile 持久化根。

本品落点（B17）：

- 新增独立 profile `eterna-acp`：bundles `[dsh-base, dsh-acp-app]`，patch 复用
  C1–C4 的遥测/账号裁切，`llm-pi-ai` 走三家直连（ACP 初始 provider 建议
  `mimo` / `mimo-v2.6-pro`），persona 换成本产品；
- 新增 `docker/profile/package.acp.json` + `profiles/eterna-acp/cordis.patch.yml`；
  entrypoint 增加 `ETERNA_FORM=acp` 分支：**所有日志改走 stderr**，不启动 relay、
  不启动 web server，最后 `exec dsh --profile eterna-acp`；
- compose 增加可选 service `eterna-agent-acp`（`profiles: ["acp"]`、`stdin_open: true`、
  `tty: false`、无端口、同 `/data` 卷）；客户端用
  `docker compose --profile acp run --rm -T eterna-agent-acp` 驱动；
- 安全边界：ACP 是受信控制器，能读写 `/data` 下全部租户数据；**只允许运维/管理员在
  本机启动，不暴露网络、不发给终端用户**。ACP 的 `cwd` 是容器内绝对路径；IDE 若要
  绑定宿主机项目，必须把项目以相同路径 bind mount 进 ACP 容器（另立部署项）；
- 并发：ACP 与 web 进程共享 `/data`；不同会话可并行，但同一工作区的导入/ACP 写入
  要串行化测试；48 号 FUSE 浸泡必须覆盖“web + ACP 同时写”。

### 2.15 WebWorker 与 terminal-panel：已拍板结论

两者都不是“加一行就完事”的能力：

- `webworker-runtime` / `webworker-packer` 是**浏览器 Worker 预览运行时**：把整棵
  harness 插件树打进 VFS 镜像，在浏览器里跑；缺 `node:sqlite`、`node:net`、原生 TLS、
  真子进程、Office 转换、Pi Agent、PTC Node 程序、宿主包管理等能力，且沙箱只是 VFS
  边界不是内核 Landlock。**v7 已拍板：不产品化**（T6）；只保留为预览/回归工具的调研
  结论，不进镜像、不进生产 profile。
- `terminal-panel` 是**侧栏持久终端的 UI/后端**：模型侧 6 个 `terminal_*` 工具 +
  侧栏旁观、首次按键接管。**v7 已拍板：全量应用（web+super）**（B20）；但
  `readUserTerminals:false`（共享容器没有“人自己的终端”归属），且 9 个
  `terminal/*` 动作必须先全部进 access 守卫，否则可跨用户读/注入他人会话终端。

### B14 MCP 两层化：系统层 admin + 个人层按用户（v6 拍板）

**定性**：v6 拍板「普通用户也能增删 MCP 服务器」。上游 mcp-manager 只有**全局 plane**
（README：「The manager governs the global plane only」），其 `servers` 是每个 Host 一份，
stdio 条目可拉起任意 `command`——把写权限直接开给普通用户，等于让任一租户在共享容器里
执行任意命令并读取其他租户数据（H14）。因此产品做**两层**，而不是把全局表开放：

| 层 | 管理者 | 存储 | 可见范围 | 传输 |
|---|---|---|---|---|
| **系统层** | admin | `profiles/<name>/cordis.patch.yml` 的 `mcp-manager.config.servers` | 全 Host（所有租户的 Agent 都能看到） | stdio / HTTP，由 admin 决定 |
| **个人层** | 每个登录用户 | 产品自有 per-user 表（见下） | **只在该用户自己的 Agent 作用域内** | stdio 仅管理员目录；HTTP `http:`/`https:` 任意 host（白名单暂关，元数据地址仍拒） |

**关键事实**：mcp-client 的 `serverName` 只在 registration scope 内唯一
（`mcp-client/src/index.ts:55-67`），且「Independent Agent scopes may reuse the same
namespace because their tools and transports are isolated」。上游
`browser-use-runtime/src/mcp.ts:120-140` 已给出可复用的模式：`createScope(ctx, agent)`
→ 在该 scope 内 `ctx.plugin(McpClient, Config({serverName, …}))` → 用
`tools/execute` 守卫拒绝非本 Agent 的调用。个人层按此模式实现。

**配置（系统层）**：

```yaml
- id: mcp-manager
  name: '@deepseek-ai/dsh-mcp-manager'
  inject: [credentials]
  config:
    servers: {}          # 产品默认空；全局服务器仅 admin 可写
```

**依赖与包位**：`packages/access` 新增 `@deepseek-ai/dsh-scope`（`createScope`）、
`@deepseek-ai/dsh-mcp-client`（子实例挂载）与 `@deepseek-ai/dsh-agent` 类型；
系统层 mcp-manager 仍由 profile 行装载。个人层不新增 bundle/profile 行（避免全局
装载面扩张），代码落在 access 的 Host 半边与 settings client 半边。

**个人层数据模型**（放 `packages/access` 的现有用户库，随 `/data/access` 持久化）：

```sql
-- 每用户一行服务器定义；name 为用户可读名，server_name 为宿主命名空间
CREATE TABLE mcp_personal_server (
  id            TEXT PRIMARY KEY,
  user_id       INTEGER NOT NULL,
  name          TEXT NOT NULL,              -- 1..64，用户可见
  server_name   TEXT NOT NULL,              -- 'p<uid>_<slug>'，[A-Za-z0-9_-]{1,32}
  transport     TEXT NOT NULL,              -- 'stdio' | 'streamable-http'
  catalog_id    TEXT,                       -- stdio 必填：管理员目录条目
  command       TEXT,                       -- 仅由 catalog_id 解析，不接受用户直填
  args_json     TEXT,                       -- 仅由 catalog_id 解析
  url           TEXT,                       -- http：http/https 任意 host；元数据地址除外
  headers_json  TEXT,                       -- 仅允许 ${secret:REF} 占位，不存明文
  enabled       INTEGER NOT NULL DEFAULT 1,
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  UNIQUE(user_id, server_name)
);

CREATE TABLE mcp_personal_secret (
  id          TEXT PRIMARY KEY,
  user_id     INTEGER NOT NULL,
  ref         TEXT NOT NULL,                -- 用户输入的名字，如 GITHUB_TOKEN
  ciphertext  BLOB NOT NULL,                -- AES-256-GCM，主密钥来自 .secrets/，不落库
  created_at  INTEGER NOT NULL,
  UNIQUE(user_id, ref)
);
```

**个人层增删改（路由与 UI）**：

1. 只走 access 拥有的端点（路由面独占，tenant-scan 强制）：
   `/api/mcp-personal/{list,upsert,delete,probe}`；请求/响应必须是 RPC 信封
   （`packages/access/src/client/rpc.ts` 是唯一信封构造点），未登录 401。
2. `list` 只返回 `userId = 当前会话用户` 的行；`upsert/delete` 只允许操作自己的行；
   任何 `id` 属他人一律 403（不区分“不存在/无权限”，防枚举）。
3. `upsert` 服务端逐字段校验：`server_name` 由服务端生成（不信任客户端）；
   stdio 的 `catalog_id` 必须在管理员目录里，`command/args` 由目录解析后落库，
   用户提交的 `command/args` 字段直接拒绝；HTTP 的 `url` 接受 `http:`/`https:`，
   **允许 localhost、私网与任意域名（v7 拍板：白名单暂关）**；仅拒绝云元数据地址
   （`169.254.169.254`、`fd00:ec2::254`）与非法 URL；管理配置保留
   `personalHttpHosts`（空数组=全放行，填入=启用白名单），未来可无代码切换。
4. `probe` 只对 `enabled` 的个人条目做一次连接/工具列表，超时 10s；
   结果只返回 `{ok, toolCount, error?}`，不回显 headers/env。
5. UI 放 `settings.section`「MCP 服务器」（v4）：admin 看到「全局 / 管理员目录」两个
   tab；普通用户只看到「我的服务器」；新增/编辑用表单，密钥字段 write-only（保存后
   只显示 `已设置`），删除两击确认，不使用原生 `confirm()`；正文 ≤3 行、强调色 ≤2。

**个人层挂载与工具隔离（H14 的核心）**：

1. 每个会话的根 Agent 创建时（`agent/created` 串行监听器，`dsh-agent` 保证它在
   释放排队工作之前完成），access 读 `sessionOwner(sessionId)` → `userId`；
   查该用户 `enabled=1` 的个人条目；对每个条目在该 Agent 的 scope 内挂一个
   `dsh-mcp-client` 子实例：`serverName='p<uid>_<slug>'`（总长 ≤32，slug 按余量截断）。
   多个条目并行连接，单条 `startupTimeoutMs=8s`；连接失败只记日志并跳过该条，
   **不阻塞会话启动超过预算**。
2. **同一 Agent 生命周期内只挂一次**；会话关闭、用户登出、条目删除/禁用时
   `scope.dispose()`，工具与连接一起卸载（mcp-client 的 disposal 已保证）。
3. `tools/execute` 守卫（与 browser-use-runtime 同构）：
   `exec.name.startsWith('mcp__p<uid>_')` 时，按 `exec.agent` 所在 session 的属主校验：
   属主 = 条目 `user_id` 才放行（**同用户的子代理/teammate 放行**），否则 `deny`；
   不按精确 Agent 相等一刀切，避免多 agent 协作时误杀。子代理若继承父 scope，
   同样走 owner 校验，不允许跨用户。
   **双保险**：复用 `tenant-plugins.ts` 已有的 `when(activation)` 归属谓词模式
   （activation 带 `agent.session.id`，`sessionOwnerOf` 查属主），在工具注册面再过滤一次；
   作用域挂载负责连接隔离，`when`/execute 守卫负责可见性与派发隔离。
4. 全局层与本层并存：`mcp-browser` 保持静态 `dsh-mcp-client` 行（`serverName=browser`），
   个人 serverName 以 `p<uid>_` 前缀避开冲突；若个人目录名与全局/插件注册名冲突，
   `upsert` 直接拒绝（不静默改名）。
5. **不把个人层写成全局 `config.servers`**：那会让所有租户的模型都看到该服务器；
   也不复用 mcp-manager 的 `register()`（插件生命周期 ≠ 用户生命周期）。

**个人层传输安全（为什么 stdio 必须走目录）**：

- 所有租户共享容器与 `/data`；stdio MCP 服务器是宿主子进程，能读 `/data/tenants/*`、
  宿主 env 与其他用户文件。**用户自填 `command/args` = 共享容器 RCE**，因此只允许
  管理员目录中的 `{command,args,envSchema}` 模板，用户只能填 env 值与启停。
- HTTP 条目由宿主发起连接。v7 拍板**接受 `http:` 与任意 host**（否则 localhost/内网
  MCP 不可用），因此存在 SSRF/内网访问面（H16，已接受）；仍拒绝云元数据地址，
  并保留 `personalHttpHosts` 空数组=放行、非空=白名单的配置开关，便于后续收紧。
  每次 upsert/probe 记审计（账号、host、结果），便于追溯；`eterna-egress` 的
  工具级出站规则不覆盖 mcp-client 的宿主连接，这一点在验收中单列。
- 个人层 HTTP 连接数/超时受 B14 限额约束；管理员可一键 `personal.enabled=false`
  关闭整个个人层（kill switch）。
- 密钥只存个人 secret 表（AES-GCM），挂载时解密后通过 `env`/`headers` 传给
  mcp-client；日志、审计、错误信息一律 `[redacted]`。主密钥只从 `.secrets/` 或
  `ETERNA_MCP_MASTER_KEY` 读，不写入镜像/argv/日志。

**限额与审计**：

- 每用户最多 8 个个人条目、同时最多 4 个连接；单条目 `startupTimeoutMs=8s`、
  `toolCallTimeoutMs=60s`、`reconnect` 上限 3 次；单用户配置总量 ≤256KB。
- 审计：`mcp.personal.upsert/delete/probe` 记账号、条目名、transport、host
  （不记 headers/env/args 原值）；拒绝记 `tenant/denied`。
- 管理员目录与全局写继续由 B14 系统层五道门收口（Settings 命名空间 gate、
  `watch/restart/probe` admin-only、漂移测试、默认空表）。

**H9 配置保留（升级前置）**：

mcp 服务器表写在 `profiles/<name>/cordis.patch.yml` 的 `mcp-manager` 行 config 内。
entrypoint 在模板变更时重渲染，现有移植不保嵌套 config → 换镜像会丢服务器。
新增 `docker/profile/migrate-mcp-servers.mjs`：

- 输入：旧 patch、新渲染 patch；
- 定位所有顶层 `- id: mcp-manager` 块，读取其 `config.servers`（YAML 安全解析）；
- 写回新渲染的 `mcp-manager` 行（替换/合并 `servers`，保留模板其余默认）；
- 逐条 fail-closed：解析失败只告警并保留模板空表，同时在
  `profiles/<name>/.upgrade-mcp-servers-backup.json` 留原始片段（0600，不打印内容）；
- 与 `migrate-prompt-edits.mjs` 的调用时序：先 prompt 移植，再 mcp 移植，最后 relay token sed；
- 升级验收：升级前后 `servers` 键数一致；启动后 `mcpManager/watch` 列表一致。

**验收**：

- **系统层**：admin 新增一个本地测试 MCP 服务器（如 `node` 跑测试 fixture）→
  工具出现在模型列表；非 admin 写 mcp-manager 命名空间 403、`restart/probe` 拒绝；
- **个人层（普通用户）**：用户 A 在 Settings 里新增 HTTP 测试服务器 → A 的会话出现
  `mcp__p<A>_*` 工具；用户 B 的会话**看不到也调不到**；B 直接 POST A 的条目 id → 403；
- **stdio 目录约束**：A 提交自填 `command` 被 400；从管理员目录选 `node` fixture 可启动；
- **HTTP 约束**：`http://localhost:<fixture>` 可成功 upsert/probe/使用；
  `http:` 与私网地址均放行；云元数据地址（`169.254.169.254`）被拒；
  `personalHttpHosts` 非空时白名单生效；
- **生命周期**：删除条目/禁用/登出后工具从会话消失；会话关闭后子进程退出；
- 容器重启后系统层与个人层条目都在；换镜像升级后都在（H9 + 个人表在 `/data/access`）；
- 审计含系统层拒绝/成功与个人层 upsert/delete/probe，均不含 token/headers 值；
- **双用户并发**：A/B 同时挂同名目录条目，各自只看到自己的实例，serverName 不冲突；
- `mcp-browser` 仍可用（浏览器执行面 E2E 不回归）。

**配置**：

  `python3 -c 'import docx, openpyxl, pptx'`。

**输出与持久化**：

- `outputDirectory=$DSH_HOME/office-kit/outputs`，provider 按 owner 建 0700 子目录；
- 保留 24h / 总量 512MB，超限按最旧淘汰；容器卸载时清理本进程输出；
- `/data` 整树挂载已覆盖（48 号方案），无需新增挂载；备份默认排除该目录；
- 巡检加一条：`du -sh /data/office-kit/outputs` 与容器磁盘余量。

**能力边界**：

- Office 工具返回的转换/重算文件在输出目录，模型需用 shell 复制到工作区
  （复制受沙箱/审批约束）；
- `office_render` 图片直接进工具结果，是视觉检查主路径；
- 侧栏 Office 预览 UI（`ui-sidebar-documentpreview`）仍裁——本产品没有
  `ui-sidebar-right`/dockkit 面，工作台有自己的文件面板；如需预览页签另立 D 项；
- 不支持系统 `soffice`/`npx` 替代转换器（上游明确拒绝）。

**安全**：

- Office 文件来自用户工作区，解析在宿主进程内（WASM）；已有输入/输出/像素/超时上限，
  保持默认并禁止调大；
- 输出目录 owner-only；不把输出写入工作区，避免越权写；
- 镜像体积增加（字体 + Python 库 + WASM）预计 200–400MB，需在构建后记录实测值。

**验收**：

- 生成样例 docx/xlsx/pptx（用预装 Python 库）→ `office_render` 出图、`office_convert`
  出 PDF、`office_recalculate` 出 xlsx；
- 中文文档渲染无 `missingFonts`（或仅缺非关键字体）；

- 删除 kit 包模拟缺失 → 工具返回 `unavailable` 且提示用户，不崩溃；
- 重启容器后 office 行仍在、输出目录可写。

### B16 chat-import 纳入（多租户桥 + 导入后记账）

**定性**：上游的“owner-only”在桌面单用户是安全边界；在本品多租户 Web 里，
unary HTTP 恒 owner Peer（H10），owner 检查等于没有。**不能直接开行**，必须先补
access 路由门与导入后记账。

**配置（默认值，不调大）**：

```yaml
- insert:
    - id: deepseek-chat-import
      name: '@deepseek-ai/dsh-deepseek-chat-import'
      config:
        maxSessions: 1000
        maxUploadBytes: 536870912      # 512 MiB；整包驻留 Host 内存
        maxEntryBytes: 268435456       # 256 MiB
        maxTitleBytes: 80              # 与 session-title 一致
```

**四道门**：

1. **请求级租户门**（`packages/access/src/mux.ts` 的 `admit` 包装，所有 `/api`
   请求必经）：命中 `POST /api/deepseek-chat-import/archive` 时，从 cookie 解析
   `eterna-user`；无会话 401；`workspaceId` 缺失 400；`store.workspaceOwner(id) !== userId`
   时 403 并审计 `chat.import.denied`（不读 body、不打印压缩包内容）。
2. **流式记账**：在 `admit` 返回的 `Response` 上包一层 pass-through
   `TransformStream`，逐行解析 NDJSON；遇到 `outcome.ok` 时把 `sessionIds` 逐条
   `store.recordSession(id, userId, workspaceId)`。**不得缓冲整个响应**（512MiB
   上传 + 导入进度必须保持流式）；解析失败只告警，不阻断响应。
3. **失败/取消对账**：导入失败、连接断开或取消时，读取
   `workspaceRegistry.get(workspaceId).sessionIds`，把 `sessionOwner(id) === undefined`
   的会话补给 workspace owner。workspace 是单属主（`store.workspaceOwner`），
   该对账不会跨租户；对账本身也走审计（`chat.import.reconcile`）。
4. **上游 owner 检查保留**：它是防御纵深，不作为本品授权依据；access 门才是真边界。

**UI 与限额**：

- 浏览器半边通过 `sidebar.session.action` 在“新建会话”行追加按钮；只对能调用
  `deepseekChatImport/limits` 的 Peer 显示。上游 `limits()` 仍是 owner 检查，
  unary 通道会通过；**不要把它当权限**，按钮可见性只是 UX。
- 先按上游按钮/对话框接入，做 v4 审计：令牌桥接、圆角阶梯、正文不出现
  `font-weight:500`、深浅主题、1100/760/640 三视口。审计不过时，保留 Host 导入链，
  用产品自有 client 半边替换按钮/对话框（不改上游源码，不新开页面）。
- 512MiB 整包驻留内存 + fflate 同步解压：容器先按默认跑 512MiB 合成包浸泡；
  若 OOM，只允许下调 `maxUploadBytes`（如 256MiB），不得调大。
- **反代配套**：NAS/Nginx 若走反代，`client_max_body_size` 必须 ≥ 512m，
  `proxy_read_timeout` 覆盖导入时长；否则浏览器侧先 413/超时。该条进部署 README。

**验收**：

- 用户 A 导入到自己 workspace → 成功，会话列表可见，`sessionOwner` 已记账，
  终端/文件面板/审批可用；
- 用户 A 带用户 B 的 `workspaceId` → 403，B 的工作区无新会话；
- 未登录 → 401；非 `application/octet-stream` → 400；
- 上传中断/损坏包 → 已写入会话仍能在 workspace 对账后可见，且 owner 正确；
- 重复导入同一 zip → 产生重复会话（记录为已知行为，不承诺去重）；
- 512MiB 合成包不 OOM；反代 512m 实测可过；
- 审计有成功/拒绝/对账三类，且不含标题与压缩包内容。

### B17 ACP 纳入（独立 profile + service）

**定性**：ACP 是自动化客户端的受信 stdio 面，不是 Web 功能；不能挂在
`eterna-web` profile 上，也不能和 web server 抢 stdout。

**文件**：

```text
docker/profile/package.acp.json          # dsh.profile.bundles = [base, dsh-acp-app]
docker/profile/cordis.acp.patch.yml.template
profiles/eterna-acp/cordis.patch.yml     # 源侧同名基座（与 web/super 同规则）
docker/acp-entrypoint.sh                 # 或 entrypoint 的 acp 分支
```

**profile patch 要点**：

- C1–C4 裁切（只覆写 ACP 组合里实际存在的行；`desktop-product-telemetry`/
  `product-analytics` 是 web-app 行，ACP 不写，避免未知 id 告警）：
  `otel`、`session-telemetry-otel`、`authorization`、`deepseek-account`、
  `llm-deepseek`、`llm-deepseek-account`、`session-log-deepseek` 全禁；
- `llm-pi-ai` 走三家直连（复用 web 模板的 provider 块；为避免双份漂移，Phase 3
  先复制并在门禁里比对两文件的 `llm-pi-ai` 块哈希，后续再抽公共片段）；
- `agent-default-model` = `provider: mimo / model: mimo-v2.6-pro`；
- `acp` 行 `config.provider: mimo`、`config.model: mimo-v2.6-pro`；
- `system-prompt.personaPrefix` = 本产品 coding agent 身份（中文对外、英文 prompt，
  与现有品牌口径一致）；
- **安全三行**：`eterna-governance`、`eterna-audit`、`eterna-egress`
  （只挂这三个，不挂 memory/knowledge/channels）；ACP 的
  `session/request_permission` 由客户端应答，治理 ask 不会被吞；
- `hmr` 与 `session-title-llm` 继续禁用（`acp-app` 已做）；
- ACP 不挂任何 `ui-*` / client 包；profile 目录只链 `@eterna` 需要的包。

**entrypoint / compose**：

- `ETERNA_FORM=acp`：
  - `PROFILE_NAME=eterna-acp`、`PATCH_TEMPLATE=cordis.acp.patch.yml.template`、
    `PROFILE_PACKAGE=package.acp.json`；
  - **所有 `echo`/诊断改走 stderr**（统一 `log()` 或逐条 `>&2`）；**禁止
    `exec 1>&2`**——它会把 dsh 的 ACP JSON-RPC stdout 一并改道；不启动 relay、
    不启动 web server；设置 `DSH_HOME=/data`、`DSH_AGENTS_HOME=/data/agents`；
  - 对 profile 渲染加 `flock $DSH_HOME/.profile-render.lock`，避免 web/ACP 同时首启
    竞争写 `profile/package.json` 与 patch；
  - 最后 `exec dsh --profile "$PROFILE_NAME" "$@"`，stdout 只留 ACP JSON-RPC。
- compose 增加可选 service：

```yaml
  eterna-agent-acp:
    image: eterna-agent:<tag>
    profiles: ["acp"]
    stdin_open: true
    tty: false
    environment:
      ETERNA_FORM: acp
      DSH_HOME: /data
      DSH_AGENTS_HOME: /data/agents
    volumes:
      - eterna-home:/data
    # 无 ports；由本机运维用 docker compose --profile acp run --rm -T 驱动
```

- 不要在 web 容器里 `docker exec` 起第二个 ACP 进程作为默认路径；独立 service 的
  stdin/stdout 边界更干净。若确要用 exec，必须 `-i` 且不得混入 entrypoint 日志。

**安全边界**：

- ACP 客户端是受信控制器：能指定任意容器内绝对 `cwd`、stdio/HTTP MCP 命令与 env；
  **只允许管理员/运维在本机启动，不暴露端口、不接终端用户**；
- IDE 要绑定宿主机项目时，必须把项目以相同绝对路径 bind mount 进 ACP service；
  容器内 `/data` 之外的路径默认不存在；
- 与 web 共享 `/data`：不同会话可并行；同一工作区的导入与 ACP 写入要串行测试；
  48 号 FUSE 浸泡要覆盖“web + ACP 同时写”；
- ACP 不提供删除/fork/回放；`session/resume` 只恢复日志，不回放历史。

**验收**：

- 用 ACP v1 SDK：`initialize` → `session/new`（绝对 cwd）→ `session/prompt` →
  `session/cancel` → `session/close`；stdout 无任何非 JSON 行；
- `session/list` / `session/resume` 跨进程可用；模型/推理档位可切换；
- 非 JSON 日志只出现在 stderr；SIGINT/SIGTERM 能 drain 后退出；
- 治理 ask 能以 `session/request_permission` 到达客户端；拒绝后工具不执行；
- 无端口暴露；无 web 静态资源；同 `/data` 下 web 会话不被 ACP 破坏；
- ACP 容器与 web 容器同时启动不争抢 profile 渲染锁。

### B18 实验 bundle 产品默认化（16 包矩阵 + 迁移）

**原则**：随镜像装入 ≠ 默认开启。产品默认集只放“低风险、与本品边界一致、
有明确用户价值”的 bundle；其余保持“插件页可开”，平台/外部依赖不满足的显式标注。

### T6 WebWorker（v7 已拍板：不产品化）

**它是什么**：`webworker-packer` 把一份随附 profile 的 bundle 打成 VFS 镜像
（gzip tar + 懒加载 chunk + overlay），`webworker-runtime` 在 dedicated Web Worker
里挂载镜像、用 CommonJS 包装加载器跑整棵插件树，经 postMessage HTTP 隧道服务页面。
用途是**浏览器内预览部署与打包回归**，不是生产运行时。

**能力边界（上游 README 实证）**：

- 缺 `node:sqlite`、`node:net`、`node:dns`、`node:vm`、`node:repl`、
  `node:worker_threads`（结构化 stub，调用即 `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`）；
- 无原生 TLS 监听、无真子进程（shell 是 Worker 内的命令表，不是 bash）、
  无宿主包管理（`execa` 拒绝）、无 Pi Agent/PTC Node 程序；
- Office 转换 `unavailable`（镜像排除 LibreOffice kit）；
- 沙箱是 VFS 边界，不是内核 Landlock；`full` 不代表任意 native 进程；
- HMR 只应用 profile 变更，不替换已加载模块；镜像必须先用仓库构建产物打包。

**对本品的结论**：本品依赖 `node:sqlite`（access/memory/usage）、原生 PTY/终端、
Office WASM、relay、审批桥、租户门禁与大量 `@eterna` 宿主插件；这些在 Worker
运行时里要么不存在，要么语义不完整。**不能作为产品运行时，也不应作为“无服务器
部署”卖点**。若未来要做浏览器 Demo，只能另建一个裁剪组合（无登录/无多租户/
无 Office/无终端），与生产镜像分开验收；本轮不投入。

**建议**：T6 关闭为“不产品化”；保留只读调研结论，不作为升级门禁项。
