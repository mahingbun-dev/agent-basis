# 27 - 执行者模型与冲突解决（Superagent vs Subagent 对照）

> 状态：**讨论沉淀**。本文回答两个架构问题：① superagent 与传统 subagent 的设计差异、各自解决的问题、如何配合；② 多智能体/subagent/superagent 如何解决"不同执行者碰同一问题"的冲突与多会话冲突。
> 定位：`24`（融合设计）· `25`（业界依据）· `26`（扩展模型）之后的**执行者权力结构与并发控制**专题，为 `packages/tasks` 的实现提供裁决规则。

## 0. 一句话结论

**Subagent 是战术单元，Superagent 是组织单元——它们不在同一层，且必须配合使用**：superagent 内部自己就在派 subagent。冲突解决的最高境界不是裁决机制，而是**让冲突在架构上无法产生**：空间分区、归一化、串行化、幂等——四道防线都在冲突发生之前起作用。

---

## 1. Superagent 与 Subagent 的设计差异

### 1.1 一句话定性

- **Subagent（子代理）是战术单元**：为父 agent 的**一个回合**服务的临时工人，解决"上下文工程"问题；
- **Superagent 是组织单元**：一个有授权、有身份、有状态、有汇报义务的**常驻团队成员**，解决"把派活变成可治理的组织流程"问题。

Superagent 不是"更大的 subagent"。判别测试：**如果这个执行者消失了，需要有人向团队解释吗？**
Subagent 消失了没人知道（父兜着）；superagent 消失了审计里少了一条链（组织要追问）。

### 1.2 逐维度对照

| 维度 | Subagent（传统子代理） | Superagent（dsh-superagent 式） |
|---|---|---|
| **启动方式** | 父 agent 在回合内派出（`tool-subagent` spawn） | 事件源触发 → 准入矩阵 → Eval 裁决 accept |
| **生命周期** | 父回合内，完成即消亡 | 跨回合、跨天、跨设备；已结束工单可被人追问恢复 |
| **上下文** | 父给一段 prompt，孤岛上下文，回传摘要 | 携带完整 Thread 上下文 + 授权凭证；Subscription 持续扇入后续讨论 |
| **权限来源** | **借用**父 agent 的权限 | **自带 Mandate**：谁授权、哪版策略、什么范围、什么强度，不可变 |
| **对外身份** | 无——只与父通信，人看不见它 | 有——以团队可见的 bot 账号直接发评论/回消息 |
| **持久状态** | 无，结果回传即丢 | SQLite + Effects + Outbox，崩溃可恢复、断点续跑 |
| **汇报对象** | 父 agent（一次） | 组织：Ticket 生命周期 + Report 六态 + Attention |
| **失败语义** | 异常冒泡回父，父自己想办法 | 结构化：`blocked`（等人）/ `failed`（重试=新分支）/ `dropped`（无需处理） |
| **并发模型** | 父说了算（3–5 个并行是常见值） | WorkerSlots 槽位制：maxWorkers、人可插队 +1 槽、唤醒优先于新 launch |
| **典型缺陷** | 隐式决策冲突、重复劳动、上下文失真（game of telephone） | 成本（约 15× token）、验证靠自述、单机单写者边界 |
| **解决的核心问题** | 主上下文污染、并行探索、专业隔离 | 授权可解释、异步可持续、注意力纪律、全链可审计 |

### 1.3 各自解决什么问题（回到第一性）

**Subagent 解决的是模型层问题**——"上下文窗口有限，而调查性工作会产生大量中间垃圾"。Claude Code 的实践给它三个约束：顺序执行、通常只回答不改动、把调查挡在主历史之外。本质是**上下文缓存管理策略**。

**Superagent 解决的是组织层问题**——"人把活交给 AI，怎么保证它被授权、被追踪、被交付、不打扰人"。其核心对象（Mandate / Ticket / Report / Attention）在 subagent 模式里**不存在**——传统 subagent 场景不需要向组织交代。

## 2. 配合使用：三层权力结构

```
组织层   Orchestrator（主 Session）：准入、路由、裁决——唯一能开票/停票的角色
战术层   Worker（工单 Session）：拥有一个 Mandate 范围内的实现，可派 subagent
执行层   Subagent：工单范围内的调查/并行探索，借 worker 的权限，只向 worker 回报
```

### 2.1 三条组合纪律

1. **Subagent 永不越过 Mandate**：它借的是 worker 的权限，worker 的红线（hitl.yaml、deny 规则）对它同样生效。本仓的 governance pre-execute 瀑布天然覆盖所有 Session（含 subagent），这一点已成立；
2. **跨工单协调必须走工单交接，不走 agent 互聊**：worker A 发现需要财务复核 → orchestrator 开新 Ticket 给财务包 worker（带引用）——跨 agent 隐式决策协调当前不可靠（`25` 号卡点 3，Cognition）；
3. **Subagent 输出落文件不落消息**（R4）：写进 `.ticket/<id>/`，避免"打字转述"的信息失真——Anthropic 实测这条能消掉大部分 telephone 效应。

### 2.2 本仓的现成资产

- `packages/extra` 的 **reviewer preset**（只读审查 subagent，工具白名单 read/grep/glob）= 标准执行层配置；
- 上游 `tool-subagent` / `tool-subagent-fork` 已在 profile 开启；DSH 约定：worker 派生的 subagent 跑 `standard` preset（前台命令 60 秒转后台，subagent 结束时其 jobs 被杀）；
- superagent 的 `executor/background.ts`（`untilQuiet` / `stopBackground`）示范了 worker 如何等待/停止自己的 subagent——移植 executor 时一并参考。

## 3. 冲突解决：五类冲突与对应机制

### 3.1 冲突分类总表

| # | 冲突类型 | 典型场景 | 解法（机制） | 谁提供 |
|---|---|---|---|---|
| 1 | **工作区冲突**（两个执行者改同一文件） | 两个工单都改同一模块 | **空间分区**：一工单一目录（隔离写） | superagent worktree/目录；Anthropic C 编译器项目 |
| 2 | **语义冲突**（隐式决策不一致） | 一个做马里奥背景、一个做不搭的鸟 | **不制造冲突**：紧耦合工作禁止并行，走单线程或工单串行 | Cognition 的核心论断 |
| 3 | **重复劳动**（干同一件事） | 模糊委派导致三个 subagent 查同一问题 | **幂等 + 查重**：稳定 trigger id（重复 accept 只建一单）；Eval 强制看到线程上所有工单（含已结束） | superagent `ids.ts` + Eval 输入 |
| 4 | **资源冲突**（并发超额/互相抢占） | 16 个工单同时要 worker | **槽位制**：maxWorkers、人可插队 +1 槽、唤醒优先于新 launch | superagent `WorkerSlots` |
| 5 | **多会话冲突**（同一会话/工单收到矛盾输入） | 追问同时从 Web 和飞书进来 | **线程串行化**：一线程同时只跑一个 Eval，期间到达的合并进下一批；工单状态只有 Engine 一个写者 | superagent Thread 规则 + Engine 单写者 |

### 3.2 五个通用机制（抽象层，实现时对照）

**① 单写者原则（最本质）**
Engine 是领域状态的**唯一事务写入者**——Trigger/Thread/Decision/Ticket/Assignment 全部经它，同步方法 + 每命令一事务。等价于数据库的**可串行化**：冲突在写入前被序列化消解。融合版继承（tasks 的 Engine）——"两个会话同时操作同一工单"在领域层**不可能发生竞态**，它们只是排队的两个事务。

**② 幂等键（防重复）**
Trigger id 从内容派生、稳定不变 → `Engine.receive` 返回 `duplicate` → 重复 accept 只产生一个 Ticket。Outbox 回执同理（同一 id 永不排队两次）。**多会话重复触发同一请求，天然收敛为一单**。

**③ 空间分区（防互踩）**
一工单一个独立目录，是 Anthropic C 编译器项目用 ~2,000 个并行 session 验证过的唯一可靠分区法。补充招法：**用外部 oracle 划分工作边界**（他们用 GCC 当"在线已知良好编译器"）——当两个 agent 的产出有公共依赖时，引入判定者切分，而不是让它们协商。

**④ 权力层级（防授权打架）**
冲突真的是"谁说了算"时，裁决顺序硬编码：

```
人的 stop（撤销 Mandate，最高）
  > 策略新版本（policyChanged 通知在跑工单，但不撤销）
    > orchestrator（唯一能开票/停票/改路由）
      > worker（Mandate 范围内自治）
        > subagent（借权，无对外身份）
```

精妙点：**策略变更不撤销在跑的授权**（只通知）——撤销会留下半成品；"是否继续"留给下一次 Mandate 再校验。宁可慢，不可烂尾。

**⑤ 人在环上（最终仲裁）**
真正无解的冲突（两个工单范围确实重叠）最后升级为人：Attention 结构化提问、面板的 stop/retry、审批。superagent **刻意不自动仲裁范围冲突**——自动仲裁 = 自动猜人意图 = MAST FM-2.2（未请求澄清）。

### 3.3 多会话冲突的三个具体防线

| 情况 | 场景 | 防线 | 冲突消失在哪一步 |
|---|---|---|---|
| **A** | 同一用户从多渠道发消息（Web + 飞书同时追问） | channels binding 多渠道收敛到同一身份 → 同一 thread/ticket → 线程串行化 + 批量合并 | **归一化** |
| **B** | 多个用户的请求互相纠缠（两人同时让改同一个东西） | Eval 强制携带"线程上所有工单（含已结束）"视图 → orchestrator 看到重叠 → `attach` 挂到已有工单而非新建 | **合并请求替代竞速** |
| **C** | 同一条消息被重复投递（webhook 重试、事件重放） | 幂等键（机制 ②） | **幂等** |

这就是为什么 `24` 号把 binding 从 `channel_user → session` 升级为 `→ thread / ticket` 列为中改项——**情况 A 的整条防线都建在这一步上**。

## 4. 诚实的边界：哪些冲突业界无解

| 无解项 | 现状 |
|---|---|
| **紧耦合工作的并行化** | Cognition 的判决仍是现状：没有共享隐式决策的机制，就只能不并行。superagent 用"单目录 + 主 Session 转述"绕开，不是解决 |
| **过程漂移**（长任务中悄悄偏离目标） | G 门禁兜产出质量，兜不住过程；只能靠金集 + 审计事后发现 |
| **自动范围仲裁** | 故意不做——机器猜意图的风险大于人工裁决的成本 |

**最重要的设计原则是消极的**：冲突解决的最高境界是**在架构上让冲突无法产生**。四道防线（空间分区 / 归一化 / 串行化 / 幂等）全部作用在冲突发生之前；真正需要"裁决"的冲突越少，系统越可靠。

## 5. 对融合设计的两条实施提示

> 以下两条为本文新增结论，待确认后并入 `24`/`26` 号的实施契约。

1. **worker 的 subagent 权限进包声明**：`26` 号 §4.1 的 `worker` 声明段增加 `subagent_policies`（如"只允许只读 reviewer 类" / "允许 spawn 但必须 standard preset"）——把 `packages/extra` 的 reviewer preset 变成包可引用的平台资产，而不是散落的配置。
2. **冲突可观测**：observe 增加一类信号，三个数字是**冲突率的直接度量**——
   - Eval 的 `attach` 次数（挂到已有工单 = 请求重叠的频率）；
   - `Engine.receive` 的 `duplicate` 比例（重复投递的频率）；
   - WorkerSlots 的插队次数（并发压力与人的介入频率）。

   试点期每日看一眼这三个数字，比任何理论论证都更快告诉你：分区边界画得对不对。阈值建议随试点基线定，先记录不告警。
