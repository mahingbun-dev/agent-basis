# 可执行计划书：多用户权限隔离与双层插件空间改造

> 生成：2026-11-10 ｜ 状态：待执行 ｜ 分支基线：`fix/access-tenant-bootstrap`
> 访谈产物：五条需求（含期中补充的用户删除级联销毁）+ 两轮决策确认 + 三路代码/业界考证（证据见 §11）

## 1. 一句话目标

让多用户部署下的五条硬性隔离全部成立并配 E2E 证据：**目录选择锁账号目录（树形 UI）、会话/工作区零越权可见可开、bash/终端写边界=账号目录、插件「公共层 + 个人层」双层空间（个人免审批、仅本人加载，转内置过闸）、用户删除即级联销毁其工作区文件**——一次性交付。

## 2. 背景

EternaAgent 以 eterna-access 门禁形态多账号部署（容器内单进程单 OS 用户，`DSH_HOME=/data`，每用户工作区 `$DSH_HOME/workspaces/<账号>/`）。现状盘点（2026-11-10，四路并行代码考证）：unary 写面守卫已建成，但**读/流面存在重大缺口**——`session/events` 等 8 个 unary 端点漏守卫、WS mux 流（`/api/remote.mux`）完全绕过守卫（浏览器 Peer 恒 owner），**任何人能看到并打开他人会话**；用户终端 PTY 无守卫无沙箱；插件机制是 profile 级全局共享（无账号概念）且插件页无角色门。用户据此提出五条需求（§3，第五条为期中补充），并确认：只锁写边界、可信小团队 ≤20 人共享单容器、双层插件空间（个人免审批、仅本人加载，转内置过闸）、一次性完成。

## 3. 访谈结论（已确认决策）

| 维度 | 结论 |
| --- | --- |
| 目标 | 五条需求全部满足：①工作区目录选择限账号目录+目录树 UI（禁手填/禁上一级）；②工作区/会话仅本人可见可开（前端+接口全路径）；③bash/终端写边界=账号目录（`cd ../` 不可逃逸）；④插件=公共层（核心/内置，admin 管）+个人层（本账号目录存放/发现/启用，免审批、仅本人加载）+转内置机制（个人发起需管理员审批，管理员发起直接生效）；⑤删除用户=级联销毁其工作区内容（账号目录文件夹直接删除） |
| 隔离强度 | **只锁写边界**（一期不做读隔离；`cat /etc/passwd` 可读是接受的已知限制） |
| 信任模型 | 可信小团队 ≤20 人，共享单容器单进程；不做每用户容器/OS 身份 |
| 插件产品语义 | **双层空间**：公共层=现有 bundle/profile patch 层；个人层=每用户独立（存放 `$DSH_HOME/workspaces/<账号>/plugins/`、发现=本人清单、启用=本人清单）。装载逻辑=通用配置+个人定制配置合并。**个人插件仅本人加载（其他人不加载），安装/启停免 admin 审批**；提供**转内置**机制：个人或管理员发起，个人发起→管理员审批，通过/直转后进公共层全员可用（拷贝制，个人原件自动停用标记「已转内置」） |
| 审批与消息 | 管理员需要**通用**「审批流 + 消息提醒」插件（公共层）：审批队列 + 站内消息/未读提醒（不出内网）；插件转内置申请为首个消费方，审批模型泛化供后续复用 |
| 终端处置 | 保留终端功能，**按「修改 api-terminal-controller」的意图做同协议替换件**（上游源码只读铁律，见 §4 待定项 1）：租户归属校验内聚到服务入口 + `ctx.sandbox.confine` 包装 PTY |
| 用户删除语义 | 删除用户时其账号目录（工作区文件+个人插件目录）**整目录递归删除**，不留残余；配合两击确认明示销毁范围 |
| 节奏 | 一次性完成（§7 任务序号即执行顺序，无中途验收停点） |
| 验收标准 | §8 验证方式全绿 + 五条需求逐条 E2E 实证（含深浅两主题截图，AGENTS.md 前端纪律） |

## 5. 范围

**做**：§7 全部任务（access 守卫补全、mux 流过滤、沙箱写边界、终端替换件、目录树 UI、双层插件空间、用户删除级联销毁、E2E 验收、文档同步）。

**不做**：
- 读隔离（自定义 sandbox provider 收紧 ro-bind 白名单）——一期接受读不设防；
- 每用户容器 / 每用户 OS 身份 / 进程级插件沙箱（Node 无 in-process 权限裁剪能力，业界也无先例）；
- 用户间任意直接共享与外部市场分发（Coze「发布到 store」语义不在本期；跨用户扩散唯一正路=转内置，见 T7）;
- 上游源码修改（deepseek-harness 只读）。

### 6.4 需求 4（插件双层空间）——结构性差距：现机制 profile 级全局共享

- 安装落共享 `<profile>/node_modules`（plugin-manager `operations.ts:299` runPnpm 以 profile 目录为 cwd）、发现读共享 manifest、启用写共享 `cordis.patch.yml`（`patch.ts:25-78`）——**无账号概念**，A 装的 B 立即可见可启用。
- 插件页 Web UI 无角色门（`ui-plugin-manager` 无 admin 检查）、pluginManager/pluginMarket RPC 与 `/api/plugin-manager/detail-file`、`/api/plugin-market/detail-file` 均不在守卫清单 → **任何登录用户可向共享 profile 装包/启停**（影响全体）。
- 已有关口：容器部署 agent 面 `tool-plugin-manager`/`tool-plugin-market` 已 disabled（docker/profile patch 模板 :276-281,408-413,97-98）；admin 实例级启停（TOGGLEABLE_PLUGINS，`packages/access/src/routes.ts:43-146` + entrypoint 渲染裁剪 `docker/entrypoint.sh:29-50`）。
- 上游装载管线（改造依据，`dsh-app-boot` 0.2.2-rc.1）：
  - patch 优先级（后位覆盖前位）：bundle 层 → profile `cordis.patch.yml` → `$DSH_HOME/cordis.patch.yml` → `--patch` overlays（`app-boot/src/profile-context.ts:74-85`）。
  - **运行时动态装卸 seam 存在**：hmr 行 watch patch/manifest → `reconcileProfile` → `recomposeProfile`（`app-boot/src/index.ts:305-432`）——运行中进程可挂/卸插件行。
  - **工具注册表是 ScopedLayers 按 scope 分层**：`tools.register(def,{when})` 注册进调用 ctx 的 scope 层；`tools.restrict({allow,deny})` 沿 scope 链求交集（`core/tools/src/index.ts:128-227`）；**每个 Session 有 scope**（session-controller `service.ts:618` createScope）且 preset 机制示范了 `bindScopeParent` 挂链（`agent-preset-registry/src/index.ts:266-290`）——「session→用户 scope」父链是上游未组合但公开可行的路径。
  - cordis isolate realm：`ctx.isolate(name,label)` 同 label 相连异 label 隔离（cordis context.ts:109-125）；本仓 `packages/extra/docs/tenant-realm.md` 已约定 `eterna:tenant-realm:<key>` label（现覆盖 memory/knowledge/storage）。
  - 阻断点：settings/configEditor 写 patch 是 profile 全局按 entry id 寻址，**无 per-user 维度**——个人层配置必须以进程内对象（scope/realm/记账表）承载，不能走 patch 文件。

### 6.5 业界调研结论（双层插件的架构参照）

| 方案 | 可迁移点 |
|---|---|
| **WordPress multisite**（最同构） | 共享代码库一次装载 + per-site activation 记账（`active_plugins` option）+ 每请求合并解析有效插件集；mu-plugins=强制公共层 |
| MCP (Claude Code) | 分层配置**同名整体替换**（不做字段级深合并）+ 首次启用审批 + 工具级 allow/deny（deny→ask→allow） |
| VS Code profiles | 共享安装池 + per-profile 启用清单；「agent 引用=推荐不强制」；教训：不做快照式下发（全局层更新后副本漂移），要运行时合并 |
| Dify | workspace 作用域 + 独立 daemon 进程 + 包签名；教训：隔离面自身是新攻击面（CVE-2026-41948） |
| JetBrains（反面） | 全局状态插件做不了 per-project 过滤 → 个人插件必须「无进程级全局副作用」 |
| 安全共识 | 进程内插件=宿主同权是业界普遍现实；缓解=**安装面信任闸门**（审批/签名/allowlist）+ 能力声明 + 调用面过滤，而非进程沙箱 |

**本期决策（可信小团队，2026-11-10 用户拍板）**：个人层**免安装审批**——与业界「安装面闸门」路线刻意偏离；信任边界改为「**仅本人加载**（严格 user scope 三面过滤）+ **转内置审批闸**（扩散到全员才过审）+ 安装/启停审计」。前提是团队成员可信（≤20 人）；对外开放/招募外部成员前必须重审此决策（见 §9 风险）。

### 6.6 需求 5（删除用户级联销毁）——现状只删账本，文件残留

- 现有删除链路：admin UI 两击确认（`client/sections.tsx:158,227-234`，文案「删除」→「确认删除?」）→ `DELETE /access/api/users/<id>`（`routes.ts:344-359` handleUserDelete，admin 门禁已有）→ `store.deleteUser`（`store.ts:234-245`）：级联清 sessions/workspaces/users 三表登记行（FK 约束所需）。
- **缺口**：文件系统上的 `$DSH_HOME/workspaces/<账号>/`（工作区内容 + T6 后的个人插件目录）**原封不动**——被删用户的文件永久残留磁盘，且无任何清理机制。
- 现有护栏可复用：删自己/最后一个 admin 拒绝（`store.ts:235-240`）；审计事件 `access.user.delete`（`routes.ts:357`）。

### T2 mux 流隔离（2-3 天，`packages/access`）——选型已定（principal 换血 + registerPolicy）

**定案（2026-11-10 源码考证）**，主轴四步：
1. merge principal kind：`declare module '@deepseek-ai/dsh-typert-protocol'` 声明 `PrincipalMap['eterna-user'] = {kind:'eterna-user', userId}`（照抄 liveshare `viewer-principal.ts:16-35` 先例）。
2. **换血**：包装 `HostConnectionService.admit/admitConnection`（client-connection rpc-host.ts:129-162）——解析 `eterna_session`（session.ts:94 resolveUser）→ `connection.createPeer({principal:{kind:'eterna-user', userId}})`（按用户缓存、release 时 dispose）。上游无 per-connection identity seam，此为组合层 monkey-patch：**配防漂移测试**（admit 行为断言）并列入上游 feature request（principalResolver seam）。
3. **policy**：`ctx.remoteAccess.registerPolicy('eterna-user', policy)`——bindings(p) 按归属账本（`store.workspaceOwner/sessionOwner`）返回 `{kind:'workspace'|'session', id}` 绑定；此后流 open 越权抛 `remote-access/denied`、follow/list/快照静默过滤、事件静默丢**全部由上游 decide 链自动生效**（gateway index.ts:802-825 prepareInvocation / broadcastRemoteEvent / workspace-controller follow visible 过滤）；归属变更调 `ctx.remoteAccess.invalidate(principal)`。
4. **实施检查点**：unary fetch 精确路由带 owner-only 检查（rpc-host.ts:219-222）——换血对 unary 通道的影响先实测：若非 owner 被拒 → **换血只作用于 WS mux 通道**，unary 维持 owner Peer + 现有 cookie 守卫（T1）双保险；以实测结论回填本条。

验收（E2E，双账号）：账号 B 侧边栏**看不到** A 的工作区/会话条目；B 用 A 的 sessionId 发起 `session/follow` 得拒绝/空流；HTTP 直调 `POST /api/session/events`（T1 已堵）与 mux 两条路都测。

### T7 审批流 + 消息提醒插件（通用）与插件转内置（3-4 天，新包 `packages/approval-flow` + T6 装载器扩展）

**A. 新通用插件 `@eterna/approval-flow`（公共层，登记 `TOGGLEABLE_PLUGINS`，可缺席降级——停用后转内置申请不可用）**

**B. 插件转内置机制（T6 装载器扩展）**

1. **个人发起**：「我的插件」点「转内置」→ `ctx.approvals.register('plugin-promote', {plugin}, requester, deciders=admin)` + 消息通知管理员；管理员审批通过后执行，驳回则消息回执（原件不动）。
2. **管理员发起**：admin 插件管理页对任意用户插件直转，**免审批即时执行**。
