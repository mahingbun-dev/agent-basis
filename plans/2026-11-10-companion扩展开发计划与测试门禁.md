## 一、门禁治理原则（导读）

> 本节为装配导读，按文档装配要求突出贯穿四组门禁的治理原则；其完整原文收录于 §二.4「门禁治理原则」（DEV-PLAN §4），四组门禁段落的组级条款（GATES-CORE「执行者指定与独立性条款」、GATES-COMPAT「执行者独立性总则」、GATES-UX「执行者独立性与判定纪律」、GATES-E2E「共同纪律」）与之一致。

**1. 独立执行**——门禁判定由独立于实现者的执行方作出（CI 流水线自动项 + 非实现者的人工验收项分离）；实现者提交工件与自测证据，但不得既实现又判定。各门禁的执行者由**用户本人书面指定**（或用户本人亲自担任），指定记录随验收索引归档；实现者及其关联会话（同一代理实例或同一会话谱系）无指定权、不得自任执行者——实现者换会话自称「独立验收代理」作出的任何判定一律无效，指定记录缺失的门禁运行无效，须补指定后重跑。

**2. 证据留痕**——每次门禁运行（**无论通过或失败**）必须留存可复现证据：执行的命令与退出码、输出、矩阵逐格记录与双主题截图、失败样本；**无证据记录的「通过」一律无效**。全体系设唯一受跟踪验收索引 `acceptance/INDEX.md`，登记门禁 ID、执行人（含用户书面指定记录引用）、执行日期、结论、证据目录指针与关键工件 SHA-256 指纹；失败记录永久保留并登记「失败-修复-重跑链」。各组证据物理目录按组约定归档（GATES-CORE：`artifacts/gates/<门禁ID>/`；GATES-COMPAT：`<扩展包>/test-evidence/E2.5-compat/<门禁ID>/`；GATES-UX：`.acceptance-evidence/G-UX-XX/`（gitignored）；GATES-E2E：`acceptance/e2e-<验收日期>/`）。

**3. 禁止实现者自行判定通过**——门禁结论只能由门禁执行方出具；实现者对结论有异议走升级链，不得自行修改判据、阈值、验收范围或跳过门禁；放行以独立验收人签署为准，实现者与任何自动化流程无宣布权，其任何单方面「已完成/已通过」声明一律无效。

**4. 门禁从需求而非代码出发**——全部门禁仅从需求目录（statement/scenario/source）与两份计划书原文推演，不以任何假想的实现代码为依据（产品代码尚不存在）；门禁只约束「用户可观察到的行为」与「可客观核对的记录」，通过标准全部为布尔 / 数值 / 截图比对 / 命令退出码级可客观判定；实现者一律只承担「提交证据」义务，无判定权。

**5. 失败处理链与交付判据**——任一门禁未通过即阻断（相关工件不得合入、该阶段不得宣布完成、后续依赖阶段不得开工）；打回后按失败证据限期修复并重跑**同一门禁**，修复不得降低标准、缩小验收范围或换用更宽松的替代检查充数；同一门禁连续两次打回、门禁之间存在矛盾、或门禁本身不可执行/判据缺失时，升级至技术负责人与用户裁决，升级期间维持阻断。全部开发内容（包括扩展端、中继服务、工具层、页面提示与文档交付物）一律经过其挂接门禁组的对应门禁，任何任务不得以「临时 / 内部 / 调试 / 仅本地」名义免检；整条路线最终必须通过总验收门禁组的端到端验收（北极星场景 A–E 全场景通过 + 全量复核通过）才算交付，未通过总验收门禁组验收的任何中间状态一律不视为交付。

### 3. 阶段依赖与时序

**主串行链**：E0 → E1 → E2 → E2.5 → E3 → E4 →（可选）E5 → 总验收。串行理由：E1 依赖 E0 骨架与 D9 路线裁决；E2 的工具面收敛以 E1 闭环为地基；E2.5 的裁剪对象是 E2 定型的工具面；E3 的协作/授权 UX 不应在将被 manifest 裁剪的能力面上建造；E4 的鉴权融合与上架披露以 E3 审批/授权模型定型为前提；每阶段出口 = 该阶段挂接门禁组全绿（见 §4；E4/E5 的出口门禁为总验收组 G-E2E-01～08，在阶段收口时先行执行，见 §4 注 2），未过门禁不得进入下一阶段。

**可并行点**：

- E1-T1（扩展端）与 E1-T2（中继服务）并行，先行冻结 CDP 帧协议契约；E1-T3 汇合两者，E1-T4/E1-T5 可与 E1-T3 尾部并行；
- E2 内部：E2-T2（断线体系）可与 E2-T1 并行启动；E2-T3/T4/T5/T6/T7 在 E2-T1 之后互相独立，可并行推进；
- E2.5-T1/T2 只依赖 E0/E1，可在 E2 后半程提前并行开工；E2.5-T3/T6 必须等 E2-T1 定型；
- E3-T1 的 optional 授权接口可与 E2.5 尾部交叉准备，但 E3 主体建议在 E2.5-T6 矩阵验收通过后开工；

**注 1（E0-T3 顺延口径）**：红线清单「定版与入库」本身在 E0-T3 完成（用户本人签核，登记验收索引，作为后续红线门禁的判定基准工件）；其行为级验证无法在无可运行构建的 E0 执行，顺延至首个可运行构建起由 G-UX-10（isTrusted）/G-UX-11（URL 旁路）/G-UX-12（untrusted）/G-UX-13（敏感动作与凭据）承接——该四门禁触发时机原文即为「首个可运行构建起」，与 E0-T3 之间无覆盖真空。

**需求缺口登记（第 1 轮修订新增，编号待需求目录所有者补录）**：

1. **多激活互斥/排队语义**：同一浏览器内多个 eterna 会话并发驱动同一浏览器时的 attach/驱动互斥与排队——现需求目录（R-01～R-42）无对应编号，登记为缺口；拟以与 R-29（sidecar attach 互斥）同构的语义补录，落 E3 阶段（任务行 E3-T9 占位，门禁定义随需求补录后在协作与安全门禁组补充，补录前该任务不得开工）。

**治理原则**：

1. **独立执行**：门禁判定由独立于实现者的执行方作出（CI 流水线自动项 + 非实现者的人工验收项分离）；实现者提交工件与自测证据，但不得既实现又判定。执行者由**用户本人书面指定**（或用户本人亲自担任），指定记录随验收索引归档；实现者及其关联会话无指定权、不得自任执行者——与四个门禁段的组级独立性条款一致（第 1 轮修订补强）。
2. **证据留痕**：每次门禁运行必须留存可复现证据——执行的命令与退出码、输出、矩阵逐格记录与双主题截图、失败样本；无证据记录的「通过」一律无效。现有验证基建可作证据来源（需求目录 testInfra）：`pnpm verify`（oxlint+tsc+vitest 递归）、`pnpm lint/test`、CI verify job（含 `packctl tenant-scan`、`dsh-evals t14-replay`）、`node scripts/verify-eterna-web.mjs`、`node scripts/verify-governance-e2e.mjs`、真会话冒烟 `scripts/smoke.mjs`；带客户端包 verify 先跑 build:client。兼容矩阵（E2.5-T6）与北极星场景（X-T1）为真浏览器人工项，以逐格/逐场景记录留痕，不可用自动化冒烟替代充数。**证据根目录与验收索引统一约定（第 1 轮修订新增）**：全体系设唯一受跟踪验收索引 `acceptance/INDEX.md`——每次门禁运行（**无论通过或失败**）登记一行：门禁 ID、执行人（含用户书面指定记录引用）、执行日期、结论、证据目录指针、关键工件指纹（录屏/勾选单等关键工件的 SHA-256）。各组证据物理目录保持组约定（GATES-CORE：仓库根 `artifacts/gates/<门禁ID>/`；GATES-COMPAT：`<扩展包>/test-evidence/E2.5-compat/<门禁ID>/`；GATES-UX：`.acceptance-evidence/G-UX-XX/`（gitignored，含浏览内容一律不入库，索引登记路径与指纹）；GATES-E2E：`acceptance/e2e-<验收日期>/`），放行单与跨组追溯一律引用索引条目而非散落路径；失败记录永久保留并在索引登记「失败-修复-重跑链」。
3. **禁止实现者自行判定通过**：门禁结论只能由门禁执行方出具；实现者对结论有异议走升级链，不得自行修改判据、阈值、验收范围或跳过门禁。
4. **失败处理链**：
   - **阻断**：任一门禁未通过即阻断——相关工件不得合入、该阶段不得宣布完成、后续依赖阶段不得开工；
   - **打回**：实现方按门禁给出的失败证据限期修复后，重跑**同一门禁**；修复不得降低标准、缩小验收范围或换用更宽松的替代检查充数；
   - **升级**：同一门禁连续两次打回、或门禁之间存在矛盾、或门禁本身不可执行/判据缺失时，升级至技术负责人与用户裁决；升级期间该阶段维持阻断状态，裁决前不得以任何名义放行。

**交付判据（明示条款）**：本计划的所有开发内容——E0–E5 每个阶段的每个任务，包括扩展端、中继服务、工具层、页面提示与文档交付物——都须经过其挂接门禁组的对应门禁，任何任务不得以「临时 / 内部 / 调试 / 仅本地」名义免检；且整条路线最终必须通过**总验收门禁组的端到端验收**（北极星场景 A–E 全场景通过 + 全量复核通过）才算交付，未通过总验收门禁组验收的任何中间状态一律不视为交付。

5. **chrome://、Web Store 等不可 attach 页面**上的用户指令应得到如实不可用说明——错误质量主门禁归 GATES-CORE（R-10），本组仅登记场景（G-UX-16 第 4 项按 R-19 口径先行里程碑核查，G-E2E-17 第 8 项最终收口复核）。
6. **组边界**：R-07（断线恢复）、R-10（错误质量）、R-11/12/13/14/17（兼容矩阵与工具面裁剪主体）、R-30/31/32/34（北极星场景端到端）由其他门禁组承接；本组仅在其交叉面上引用（G-UX-01/02 引 R-13/R-15/R-17，G-UX-09 引 R-12，G-UX-07 引 R-31）。

**门禁ID**：G-UX-01
**需求依据**：R-18（辅：R-12、R-13、R-40）
**触发时机**：E3「optional per-site host 授权」任务完成后、E3 里程碑验收前首验；E4 发布前复跑一次（回归）。
**前置条件**：Chrome ≥133 真实窗口（非 headless；能力以 relay 握手 capability manifest 的 hostAccessRequest 实测值为准，不以版本号假设，见 R-12/R-13）；companion 扩展已加载（unpacked 或商店包）；可登录 eterna 会话且 relay 已连接（localhost 即可，见 R-05）；全新 Chrome profile；两个未授权过的可访问测试站点 A/B（本地静态站）；录屏工具。
**执行者**：独立验收代理（或用户本人），实现者不在场；实现者只能提交构建产物与《授权 UI 形态说明》作为证据，不得参与判定、不得宣布通过。
**步骤**：
1. 全新 profile 加载扩展、登录 eterna、连接 relay，确认连接状态正常（否则先解决前置，不进入判定）。
2. 会话让 agent「打开站点 A 并读出页面标题」；记录授权请求出现时机、形态与持久范围的声明原文。
3. 先不授权观察 agent 动作结果；再重新触发并在授权 UI 选择「始终允许本站」（或 UI 实际提供的最持久选项，记录选项原文）。
4. 让 agent 在站点 A 完成第二次独立操作（如再取一次快照）。
5. 让 agent 打开同站第二个标签页再操作（若声明为「本站」级）。
6. 关闭浏览器重开、重连后再次让 agent 操作站点 A。
7. 让 agent 操作站点 B，并在授权请求出现时选择「拒绝」。
8. 在 Chrome 扩展管理页手动撤销站点 A 授权（用户真实撤权路径），再让 agent 操作站点 A。
**通过标准**：
1. 首次操作前出现且仅出现一次用户手势触发的授权请求；授权成立前 agent 对站点 A 无任何成功动作（判定：录屏 + 审计导出中站点 A 授权前成功调用数=0，按 tab/标签标识过滤——字段标准见 G-UX-14）。
2. 步骤 4/5/6 中，凡授权 UI 已声明持久的范围内操作，授权请求出现次数=0；范围外操作必须再次请求——声明范围与实际打扰范围不一致即本条不通过（判定：录屏逐段计数）。
3. 站点 B 被拒后该站工具不可用，且会话出现如实的不可用说明，非静默失败、非假装完成（判定：会话导出含拒绝/不可用文案 + 审计导出站点 B 成功调用数=0）。
4. 手动撤权后 agent 行为与从未授权一致（判定：再次出现授权请求或如实不可用说明，录屏）。
5. 授权授予与拒绝各在审计日志留下一条记录（判定：审计导出含对应条目，联动 G-UX-14）。
**证据留痕**：全流程录屏、授权 UI 截图（含持久范围声明原文）、撤权前后截图、会话导出 JSON、审计日志导出，存 `.acceptance-evidence/G-UX-01/`；CHECKLIST 记录每条标准判定值。
**失败处理**：阻断 E3 合入，打回重做；修复后从步骤 1 全量重跑（不得只跑失败步骤）；若属 Chrome per-tab 平台语义与声明文案不一致，作为待裁决项升级用户裁决，裁决前按从严口径（范围外必须再次请求）执行——禁止以任何形式自行判定通过。

**前置条件**：服务端中继与工具层实现可供静态审查（E4 时点）；G-COMPAT-04 证据可获取（L0/L1 路由）；G-CORE-01 基准任务或场景 A 的会话导出可获取；《服务端 egress 白名单》清单文档与出站连接日志可读；本地抓包/流日志通道可用；E5 立项则 G-E2E-07 证据可获取。

**执行者**：独立验收代理（静态审查与抓包核验）；实现者权限边界：仅可提交白名单清单、代码位置指引与日志证据，不得执行判定、不得宣布通过。

**步骤**：
1. 【静态审查·出站面】审查服务端中继/工具层的网络出站路径清单：应仅含——扩展 wss 入站（出站方向无新增）、既有模型通道（LLM API，既有出站面）、sidecar 本地/受控通道（E5 范围）、tool-web 抓取出站（既有 tool-web 能力，引用其既有边界）；对照《服务端 egress 白名单》文档逐项核对，标记任何白名单外或未申报的出站路径；审查记录由验收代理签署。
2. 【运行期·出站面】在场景 A–E 执行期间（或专门执行一轮基准任务期间）采集服务端出口连接日志/抓包：核对除白名单内目标外，**新增公网出站连接数 = 0**（日志计数；白名单外任何连接即计数>0）。
3. 【路由落点·扩展主】连接徽标绿色（扩展已连接）时下达浏览器任务：任务由用户浏览器执行（tab 在用户浏览器打开，引 G-CORE-01/场景 A 证据核对，非 sidecar/服务端执行）。
4. 【路由落点·tool-web 静底】非 Chromium 浏览器或未装扩展且 sidecar 未配置时下达浏览器任务：任务落 tool-web 且页面/会话明示（引 G-COMPAT-04 步骤 2/4 证据核对）。
5. 【路由落点·sidecar 兜底】（E5 立项时）扩展不可用且 sidecar 已配置时下达任务：任务落 sidecar 并明示「服务端浏览器执行、登录态不可用」（引 G-E2E-07 场景 2/3 证据核对；E5 未立项则本行记「挂起-依赖 D1/D12 裁决」，处置结论入放行单）。
6. 【静默改道检查】逐行核对上述路由落点的会话导出：每次降级/改道均有明示，无任何「未提示即静默改道」。

**通过标准**：① 静态审查结论为「出站路径仅白名单内通道、无新增公网出站面」且签署（记录文件）；② 运行期白名单外新增出站连接 = 0（日志计数输出留存）；③ 路由三行落点各有证据且与实际执行面一致（会话导出+截图/录屏核对；sidecar 行在 E5 未立项时以挂起+处置结论代之）；④ 静默改道数 = 0（会话导出逐条核对）。①–④ 全真→通过；sidecar 行挂起不影响其余三行判定，但 G-E2E-20 放行单必须列明该挂起与处置结论。

**证据留痕**：`acceptance/e2e-<日期>/gate-21/`：静态审查记录与签署、egress 白名单文档副本、出站连接日志与计数输出、路由落点核对表与会话导出引用、（如适用）G-E2E-07 证据引用。

**失败处理**：白名单外出站连接>0 或静态审查发现未申报出站路径 = P0 缺陷：立即阻断放行，升级人工通报，打回实现者修复后全步骤重跑；路由落点错配打回修复后对应行重跑；sidecar 行挂起无处置结论不得放行；禁止以任何形式自行判定通过。
